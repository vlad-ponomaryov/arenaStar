## Рецензия (2026-10-18)

**Вердикт:** после правок ниже ТЗ готово к пошаговой реализации. Сверено с кодом на `2b37173` (Core, Bots, `MatchRunner`, виды и HUD,
asmdef, `Tools/*.ps1`, тесты — 388 EditMode + 3 PlayMode). Bootstrap-сборка перепроверена: Core + Bots + зонд с UDP (dual-stack), JSON,
SHA-256 и `TcpListener` собраны встроенным в Unity Roslyn и запущены на встроенном .NET 6.0.21 — точная команда в §5.2.

Найдено и исправлено в тексте:
- **Ловушки значений по умолчанию — ломали бы старые тесты.** `int MatchGlobals.PredictionSlot` («−1 — нет») после `State.Clear()`
  и в `new MatchState()` равен 0: слот 0 попадал бы в предсказание везде, где его не выставили явно; `MatchDefs.RespawnEnabled`
  по умолчанию `false` выключил бы возрождение во всех тестах с ручными Defs. Теперь `Predicting` (bool) + `PredictedSlot` и `NoRespawn`; общее правило — значение по умолчанию нового поля
  сохраняет нынешнее поведение (§1.3, §2.5, §9.2).
- **Начало матча не было определено:** «тик старта» в `MatchStart` нельзя знать до `ClientReady`. Отсчёт стал частью шкалы тиков
  (отрицательные тики), часы клиента сходятся за 3 с отсчёта; запас ввода задан однозначно — минимум за окно (§2.3).
- **Предсказание:** таблица исключений заменена правилом «действует только свой боец, эффекты — только свои на себя, кроме урона и
  лечения»; тень пересобирается на каждом новом снапшоте (иначе чужие в тени застывали на старых местах), скрытые враги в тени
  неактивны (иначе свой снаряд упирался в устаревшую позицию спрятавшегося); `LastAppliedInputTick` — подтверждение ввода, а не
  начало пересчёта; правило переноса опоздавшего нажатия (фронт, один прицел на тик) (§2.4, §2.5).
- **Две временные линии на одном экране:** виды и HUD сравнивают тиковые поля сущностей с `state.Globals.Tick`, а свой боец и чужие
  живут на разных линиях. Добавлено правило состояния показа и контракт `IMatchDriver` «тик за тиком, как офлайн» вместо «источника
  поз» — пулы видов, телеграфы и HUD не перестраиваются (§12.2).
- **Утечка скрытого:** попадание союзника по врагу в кусте уходило с точкой цели. Теперь при скрытой цели событие получает только
  стрелок, без точки и слота (§4.4). Счёт желудей HUD суммирует `CarriedAcorns` бойцов — со скрытым носителем он был бы неверным;
  счёт команд переносится в `ModeState` (S3.5).
- **Компенсация лага** с пределом 250 мс не покрывала цель GDD: при RTT 150 мс и джиттере 50 мс (§8.3) враги видны с задержкой
  до ≈ 350 мс. Предел — 350 мс, история — 12 тиков; автоприцел отката считается по тем же позициям, что и попадание; эффекты, события
  и рассыпание желудей — по текущим; цель, умершая или возродившаяся в окне, — без отката (§2.8).
- **Разные платформы:** прицел квантуется как 2 × int16, а не угол (тригонометрия IL2CPP ARM64 и CoreCLR даёт разные биты); онлайн-клиент
  берёт Defs из того же пакета данных, что и сервер, а не пересчитывает их из SO на телефоне; хэш — из заголовка пакета (§2.4, §5.4).
- **Сервер на Windows:** без отключения `SIO_UDP_CONNRESET` ICMP от ушедшего клиента роняет следующий `ReceiveFrom`; `Thread.Sleep(1)`
  спит до 15,6 мс; культура ru-RU пишет «0,5» в метрики Prometheus. Добавлены меры (§3.2, §5.3, §5.5).
- **Протокол:** у сегмента снаряда не было идентичности (отскок путался с новым снарядом в том же слоте) и точки конца; «ключевой
  кадр = база 0» конфликтовал с тиком 0; события повторялись «до подтверждения» — объём рос с RTT и не был учтён в бюджете. Теперь
  у сегмента есть `SpawnTick`, маска попаданий и конец, у ключевого кадра — флаг, события — подмножество, которое читают виды,
  с фиксированной избыточностью 3 тика. Добавлены флаг «своим бойцом управляет бот» и личный итог выбывшего `Eliminated` (§4.2, §4.4).
- **Упрощения без потери требований:** фрагментация убрана — самое большое надёжное сообщение (итог матча) ≈ 300 Б; сервер этапа 3 —
  один игровой поток (по оценке §5.7 его хватает на 100 матчей), рабочие потоки — только если покажет нагрузка S3.15; bootstrap-сборка
  с `rollForward: Major` запускается на любом .NET ≥ 6, в том числе на VPS — SDK желателен, но не обязателен (§5.2, §5.3).
- **Приватность:** `InstallId`/`installKey` удалены — постоянный идентификатор не нужен, возврат после перезапуска идёт по токену из
  `RejoinStore`; из статистики клиента убрана «корзина FPS»; LAN-обнаружение выключается на VPS (§4.2, §6.4).
- **По GDD:** добор ботами — «Новичок» (GDD §7: первые 30 кубков, а кубков у всех 0); AFK — 30 с, чтобы не срабатывать на тех,
  кто прячется в кусте (§7, §13).
- **План:** S3.7 и S3.10 тянули на 2–3 сессии — разбиты на S3.7a/S3.7b и S3.10a/S3.10b; у каждого шага есть «Готово, когда»;
  S3.1 не требует тестовых данных в коде сервера (headless-матч — с S3.2, по пакету данных); пороги «ноль поправок и телепортов»
  строгие только для условий CI из GDD, для «плохих» — мягкие (§11.1, §14).

Вопросы: Q-015, Q-016 и Q-018 закрыты решениями D-087…D-089 (человек может пересмотреть). Открыты только те, где нужен человек,

## 1. Исходные данные

### 1.1 Что требует GDD

- §3, этап 3: авторитарный сервер, матчмейкинг, добор ботов, переподключение, режим «Последний зверь».
  **Готово, когда:** 6 живых игроков с пингом до 150 мс играют без рассинхрона и телепортов, вылет и возврат в матч работают.
- §4: клиент только показывает картинку и отправляет ввод. Урон, победы и награды решает сервер. Клиент предсказывает своё движение.
- §7: боты работают на сервере. Добор — через 15 с (до 300 кубков — через 8 с), поровну между командами.
  Отключившимся бойцом управляет бот, пока игрок не вернётся (до 60 с).
- §8: играбельно при 150 мс и 2 % потерь, тик 30 Гц, интерполяция чужих (~100 мс). Снаряды считает сервер, свой выстрел виден сразу.
  Компенсация лагов с учётом пинга стрелявшего, сервер проверяет скорость, заряды, откаты и дальность. Трафик — до 10 КБ/с на игрока.
  Пинг до регионов, значок пинга (красный от 250 мс). Переподключение до 60 с. Версии клиента и сервера должны совпадать
  («Обновите игру»), техработы включаются флагом. Мониторинг. Условия CI: 150 мс, 2 % потерь, 50 мс джиттера.
  Перед софт-запуском — нагрузочный тест на 500 матчей.
- §2: свободного чата и ввода текста нет, данные не собираются, внешних ссылок нет.

### 1.2 Что меняется относительно GDD

Пользователь отказался от Photon Fusion и любых платных сервисов: нужно своё бесплатное решение под нашим полным управлением.
Устаревают: GDD §4 («Сетевой код — Photon Fusion 2», «Хостинг матчей — Edgegap», «Игровой сервер — один процесс на матч» —
у нас много матчей в процессе), §8.1 («режим Server Fusion», «хитбоксы Fusion»), §8.2 («аллокатор хостинга»), §13 («бюджет на
Photon»), а также D-038 (план подключения Fusion). Все требования к качеству (§8), правила (§2) и этапы остаются. Подбор по кубкам
и выравнивание сумм кубков (§8.2) — этап 4: кубков пока нет. Бэкенд аккаунтов (GDD: UGS) относится к этапу 4 и здесь не решается —
сервер оставляет место для отправки итога матча (§5.3). Правку текста GDD делает человек или разрешает агенту (Q-017).

### 1.3 На что опираемся в коде

- `MatchSimulation.Tick(PlayerInput[])` — шаг 1/30 с, фиксированный порядок систем (комментарий класса), `Reset`, `IsEnded`.
- `MatchState` — `MatchGlobals` и массивы blittable-struct фиксированной ёмкости (`SimLimits`: 10 бойцов, 256 снарядов,
  64 зоны, 128 статусов, 64 подбора, 2048 клеток). Есть `CopyFrom` без аллокаций и `ContentEquals`. RNG хранится в состоянии,
  используется только в `AcornsRules` (разброс желудей).
- `PlayerInput {Move, Aim, Buttons}` и `Sanitized()`: NaN → 0, длина ≤ 1, неизвестные биты отбрасываются.
  Кнопки срабатывают по фронту (`PrevButtons`), сборщик защёлкивает нажатие до тика (D-006, D-050).
- `SimEventBuffer` — события тика вне снапшота (D-008). `HitFeedback` показывает только то, что видит своя команда, а звук
  и вибрацию — когда участвует свой боец.
- `FighterState.VisibleToTeams` пересчитывается в конце каждого тика (D-024) — готовая основа серверного фильтра.
- `BotController.Update(state, defs, events, inputs)` пишет ввод только в слоты ботов. Удалить или отключить бота пока
  нельзя — это понадобится для подмены вылетевшего.
- `MatchRunner` — офлайн-цикл: аккумулятор, ≤ 4 тиков за кадр, интерполяция двух тиков (`MatchViewState`). Виды, HUD и
  `AcornsModeView` читают `Simulation.State` напрямую. `ScoreBarView.Apply`, `ResultsScreen.Show` и `AbilityHudInfo.From` принимают
  `MatchSimulation`, хотя нужны им только `Defs` и `State`. PlayMode-тесты читают `runner.Simulation` и `runner.Bots`.
- Виды и HUD сравнивают тиковые поля сущностей с `state.Globals.Tick`: телеграф (`ActivateTick`), дуга навеса (`SpawnTick`), откат трюка
  (`TrickReadyTick`), таймер и отсчёт режима. Счёт желудей HUD — сумма `CarriedAcorns` бойцов команды (`AcornsRules.TeamAcorns`).
- Defs строятся из ScriptableObject в `Arena.Data` (`ConfigConverter`). Серверу без Unity нужен экспорт этих данных (§5.4).
  Состав матча собирает `MatchSetupFactory` (Arena.Data) из SO `MatchRunnerConfig` — серверу нужен чистый сборщик (S3.6).
- Defs и состояние в тестах собираются вручную (`TestMatchFactory`), а `MatchState.Clear()` обнуляет всё. Поэтому **у любого нового
  поля Defs или состояния значение по умолчанию (0 / false) должно означать нынешнее поведение** — иначе изменится смысл старых тестов.
- `Arena.Tests.PlayMode` уже ссылается на Editor-only сборку `UnityEditor.TestRunner` — так же он может сослаться на `Arena.Net.Server`.

**Зонд** (лежит в скретч-папке, в репозиторий не попал). `Arena.Core` и `Arena.Bots` (96 файлов) собраны вне Unity встроенным
Roslyn (C# 9) против сборок .NET 6.0.21 **без единой правки**, за 0,8 с. Прогонялся матч «Жёлуди» 6 ботов
(упрощённые бойцы, тестовая карта со стенами и кустами).
- **CoreCLR .NET 6 x64:** симуляция + 6 ботов — **0,004 мс/тик** в среднем, p99 — 0,011 мс. 40 матчей подряд дают
  ≈ 8 500 матчей на ядро — это CPU только симуляции, без сети.
- **Размеры struct:** `FighterState` — 180 Б, `ProjectileState` — 68, `AreaState` — 64, `StatusEffectState` — 28,
  `PickupState` — 24, `PlayerInput` — 20, `SimEvent` — 40. Весь `MatchState` при полной ёмкости — ≈ 30,8 КБ.
  Пики за матч: 29 снарядов, 30 подборов, 18 событий за тик.
- **Детерминизм на одном рантайме:** два прогона в одном процессе и прогоны в разных процессах CoreCLR (с tiered JIT и без него,
  с отключёнными HW intrinsics) дают одинаковый хэш состояния.
- **На Mono x86 из Unity тот же код и тот же сид расходятся:** позиции отслеживаемых бойцов (слоты 0 и 3) совпадают до тика 82,
  на тике 83 уже разные.
  Матч закончился на тике 3956 вместо 4500, то есть с другим исходом. Побитового детерминизма между рантаймами и архитектурами
  нет (D-005 это и допускал), а клиент на IL2CPP ARM64 — ещё одна, третья комбинация. (Проверялся 32-битный `mono.exe`; 64-битный
  Mono редактора не проверялся, а C++-компилятор IL2CPP вправе сливать умножение и сложение в FMA — вывод не меняется.)
- **Проверка рецензента (2026-10-18):** bootstrap-команда из §5.2 собрала Core + Bots + зонд за доли секунды, зонд на встроенном
  `dotnet.exe` прошёл: UDP через dual-stack сокет `[::]` и подключённый IPv4-клиент, `System.Text.Json`, SHA-256, `TcpListener`,
  `GC.GetAllocatedBytesForCurrentThread`; `NET8_0_OR_GREATER` не определён. Подвохи: нативные dll в папке фреймворка надо исключить
  из ссылок (CS0009), диагностика csc без `-preferreduilang:en-US` идёт в кодировке консоли, культура ru-RU печатает `1,5`.

Выводы: (1) сервер на чистом .NET можно собрать уже сейчас; (2) lockstep и одноранговый rollback отпадают;
(3) ёмкость сервера ограничивают сеть и сериализация, а не CPU симуляции.

## 2. Модель сети

### 2.1 Варианты

| Критерий | Lockstep (обмен вводом) | Rollback (все предсказывают всех) | Снапшоты + предсказание своего (**выбор**) |
| --- | --- | --- | --- |
| Побитовый детерминизм между платформами | обязателен (зонд: расхождение за 83 тика) | обязателен для одноранговой схемы. Если состояние присылает сервер — это вариант 3 с предсказанием всех | не нужен: истина на сервере, клиент сверяется |
| Честность (кто решает урон) | каждый клиент сам | каждый клиент сам | сервер |
| Скрытая информация (кусты, невидимость, мины) | каждый клиент знает всё — подсмотреть тривиально | то же | сервер не присылает невидимое |
| Задержка | все ждут самого медленного | без задержки, но при 6–10 игроках частые откаты и «прыжки» чужих | свой боец — без задержки, чужие — с задержкой интерполяции ~100 мс |
| Потери пакетов, мобильная сеть | застревания | откаты | плавно: дельта к подтверждённой базе, избыточный ввод |
| Вход и возврат в матч | всё равно нужно полное состояние | то же | полный снапшот — штатная операция |
| Нагрузка на телефон | вся симуляция | вся симуляция × откаты | тень × ≤ 15 тиков пересчёта на снапшот (действует только свой боец) |
| Где хорош | RTS, 1×1 на одной платформе | файтинги 1×1 | шутеры 3×3…10 — наш случай |

Детерминизм остаётся полезным и в выбранной модели. Свой боец предсказывается тем же кодом, поэтому на одной платформе
поправок нет вовсе, а между платформами они крошечные. Сервер может воспроизвести матч по журналу ввода, а тесты сравнивают
состояния побитово.

### 2.2 Временные линии

```
                ← прошлое                                    будущее →
сервер:                            [T]                 T — тик, который сервер считает сейчас
клиент, чужие:        T − I                            интерполяция: I ≈ RTT/2 + буфер (≈ 100 мс)
клиент, свой:                                T + L     предсказание: L ≈ RTT/2 + запас ввода (1–2 тика)
```

При RTT 150 мс L ≈ 3–4 тика, I ≈ 5–6 тиков, и между своим бойцом и чужими на экране ≈ 9 тиков (≈ 300 мс).
Это неизбежная цена любого авторитарного шутера. Ниже описано, как её спрятать: §2.5–2.8.

### 2.3 Синхронизация тиков и часов

- Мастер-часы — у сервера: у каждого матча свой счётчик `T` — тик, который сервер посчитает следующим (в бою `T` =
  `MatchState.Globals.Tick`). Знать «настоящее» время сервера клиенту не нужно: он держит **запас ввода**.
- **Начало матча — отрицательные тики.** Тик старта заранее неизвестен: сервер ждёт `ClientReady` (§5.3). Поэтому отсчёт —
  часть той же шкалы: в фазе `Countdown` счётчик идёт от `−CountdownTicks` до −1 **без** `MatchSimulation.Tick`, с `T = 0` начинается
  бой. Снапшоты (ключевой кадр состояния тика 0, `serverTick = T < 0`, в блоке режима — «отсчёт») и ввод идут уже в отсчёте, поэтому
  к тику 0 часы клиента сошлись. Ввод для тиков < 0 сервер принимает в окне (для запаса), но не применяет. Тики в протоколе — со знаком
  (zigzag-varint). Клиент тоже не считает тень до тика 0 и показывает отсчёт из блока режима.
- **Запас ввода.** На каждый принятый пакет ввода сервер считает `margin = новейший тик в пакете − T` и в каждом снапшоте сообщает
  `InputMarginMin` — минимум за последние `MarginWindowTicks` (30) тиков. Клиент держит его на `TargetInputMarginTicks` (1): ошибка
  `e = InputMarginMin − TargetInputMarginTicks`; при `|e| ≥ HardResyncTicks` тик предсказания прыгает сразу (история ввода сбрасывается),
  иначе темп тиков клиента — `1 + clamp(−e × MarginGain, ±MaxTimeDilation)` (не больше 5 %). Минимум, а не среднее: он прямо задаёт
  долю опоздавших вводов, джиттер учитывается сам.
- RTT считается по подтверждениям пакетов (§3.2) и сглаживается как в TCP (SRTT/RTTVAR). Значок пинга показывает SRTT.
- Часы интерполяции: `renderTick` (дробный) идёт на 1 × `1 + clamp(InterpGain × ошибка, ±MaxTimeDilation)` за тик предсказания
  (состояние показа строится тик за тиком, между тиками виды интерполируют по `Alpha`; уточнено в S3.7b, D-097), ошибка —
  от цели `newestSnapshotTick − InterpDelayTicks`; при ошибке больше `HardResyncTicks` — прыжок. Задержка = `InterpDelaySnapshots`
  интервалов снапшота + `InterpJitterFactor` × джиттер прихода (EMA модуля отклонения интервала между снапшотами от номинального).
  Задержка адаптивная, в обычных условиях ≈ 100 мс (GDD §8.1).
- При входе в идущий матч (возврат, §7) и на первом снапшоте клиент начинает с `Tpred = новейший serverTick + ceil(SRTT / dt) + TargetInputMarginTicks`
  (исправлено в S3.7a, D-096: снапшот старше сервера на RTT/2, и ввод идёт до сервера ещё RTT/2 — итого RTT, а не RTT/2)
  и дальше подстраивается, как выше.
- Внутри логики `Arena.Net` время передаётся параметром (`now`). Никаких `Stopwatch` и `DateTime` в логике — на этом
  держатся виртуальные часы тестов.

### 2.4 Ввод

- Клиент: `LocalInputCollector.ConsumeForTick()` → `AimMagnet` → **квантование** (`InputQuantizer`). Это же квантованное
  значение уходит и в своё предсказание, и в сеть, иначе каждый тик будут систематические поправки.
- Квантование: `Move` — 2 × int8 (/127), `Aim` — 2 × int16 (/32767; ноль — прицела нет), `Buttons` — 4 бита. Итого 7 байт,
  а ввод, повторяющий предыдущий, — 1 бит. Обратное преобразование — только деление, без тригонометрии: клиент (IL2CPP ARM64) и
  сервер (CoreCLR x64) получают одни и те же биты; угол с `Cos/Sin` дал бы разные.
- Пакет ввода уходит каждый тик предсказания (33 мс): новейший тик, `InputRedundancy` (4) последних вводов — это переживает
  3 потерянных пакета подряд — и `ViewDelayTicks` для компенсации лага (§2.8). Вводы с тиком ≤ `LastAppliedInputTick` повторно
  не отправляются.
- Сервер держит буфер на слот (кольцо по тикам `NetLimits.InputBufferTicks`):
  - ввод для тика `t` из окна `T ≤ t ≤ T + MaxInputAheadTicks` кладётся в буфер (первый пришедший для тика побеждает); ввод ещё
    дальше вперёд отбрасывается и считается;
  - если ввода для `T` нет, повторяются последние `Move/Aim` **без кнопок**, но не дольше `MissingInputRepeatTicks`
    (6 тиков = 200 мс), дальше идёт нулевой ввод. Если ввода нет дольше `BotTakeoverSeconds`, бойцом управляет бот (§7);
  - у **опоздавшего** ввода (`t < T`) движение выбрасывается, а нажатие (атака, ульта или трюк вместе со своим прицелом и `AutoAim`)
    **переносится** в очередь нажатий слота (до `NetLimits.MaxPendingPresses` = 3) и применяется в ближайшем тике, где даст фронт:
    в прошлом применённом тике этой кнопки не было, и у тика нет другого нажатия с прицелом (у `PlayerInput` один `Aim`; порядок —
    как у сборщика: атака, потом ульта). Нажатия не теряются (D-006), предсказание поправится на тик-два;
  - фронт кнопок по-прежнему считает симуляция (`PrevButtons`), поэтому повтор без кнопок ложных нажатий не создаёт.
- В снапшоте сервер возвращает `LastAppliedInputTick` слота — новейший тик, для которого применён настоящий (не повторённый) ввод
  клиента. Это подтверждение для избыточности и статистика; пересчёт предсказания всегда начинается с тика снапшота (§2.5).

### 2.5 Предсказание своего бойца и сверка

У клиента есть «теневая» `MatchSimulation` (`Predictor`) с теми же Defs (из пакета данных, §5.4) и **режимом предсказания**:
`MatchGlobals.Predicting = true`, `MatchGlobals.PredictedSlot` = свой слот. По умолчанию `Predicting = false` — после `Clear()`, на сервере,
офлайн и во всех нынешних тестах поведение систем не меняется (поле `int PredictionSlot = −1` не годится: `Clear()` обнулил бы его
в слот 0). Правила режима — ветки `if (state.Globals.Predicting)` в системах Core, каждое под тестом:

1. **Действует только свой боец.** Циклы по бойцам во вводе (`ApplyInputs`: `Buttons`/`PrevButtons`), статусах (пересчёт агрегатов),
   движении, способностях, рывках, зарядах, возрождении и видимости обрабатывают только `PredictedSlot`. Остальные бойцы в тени —
   неподвижные мишени: позиция, «жив», команда и видимость берутся из показа (§2.6), тики предсказания их не меняют ни в одном поле.
2. **Эффекты** (`EffectSystem.ApplyAbility`) применяются, только если и источник, и цель — свой боец, и это не урон и не лечение
   (бафф, «Каска», «Дымок», «Совиный глаз»). Значит, в предсказании нет урона, лечения, поражений, заряда ульты от урона, талантов
   «при победе» и рассыпания желудей: HP своего — всегда серверное.
3. Свои снаряды, навес и зоны создаются и летят (для видов), упираются в стены, купола и тела показанных врагов. Подтягивание крюком
   (к стене и к врагу) не предсказывается; мины в тени не срабатывают — их взрыв приходит с сервера.
4. Регенерация, правила режима (`AcornsRules`, `LastBeastRules`) и RNG матча в предсказании не работают.
5. `VisibilitySystem` считает только своего бойца (`InBush` и маску — по тени: от неё зависит полупрозрачность своего в кусте);
   маски чужих бойцов и зон не трогает.
6. Поломка стен своим рывком или бревном в тени есть (нужна движению); на экране стены ломаются только по данным сервера.

- **Состав тени.** При сверке — `shadow.CopyFrom` из состояния, собранного по новейшему снапшоту `S` (тик `Ts`): свой боец и свои
  статусы — точно; свои снаряды и зоны — из сегментов и зон `S` (§4.4); клетки и режим — из `S`; чужие бойцы — в **показанных сейчас**
  позициях (интерполяция, §2.6), а не в присланных; бойцы, которых в `S` нет (скрыты), — `Active = false` (иначе свой снаряд упирался бы
  в устаревшую позицию спрятавшегося); чужие снаряды в тень не входят — их рисует интерполяция. После `CopyFrom` флаги
  `Predicting`/`PredictedSlot` ставятся заново (`CopyFrom` их перезаписывает), затем пересчитываются тики `Ts … Tpred−1` с вводами
  из истории. В отсчёте (`Ts < 0`) снапшот несёт состояние тика 0, и пересчёт идёт с тика 0.
- **Когда пересчитывать: на каждом новом новейшем снапшоте**, без пропуска «если совпало». Пропуск оставлял бы в тени чужих на
  старых местах и не стоит усложнения: пересчёт — не больше `MaxResimTicks` (15) тиков по ≈ 0,01 мс на ПК, на телефоне — порядка
  1 мс. Перед каждым новым тиком предсказания позиции и видимость чужих в тени обновляются по текущему показу. Если
  `Tpred − Ts > MaxResimTicks`, часы прыгают (§2.3). Ошибка предсказания для статистики и порогов — разница своей позиции на `Ts`
  (история предсказанных состояний своего бойца по тикам) и серверной.
- Если в снапшоте стоит флаг «своим бойцом управляет бот» (вылет, AFK, §7), предсказание выключается: свой боец показывается по
  точному серверному состоянию с интерполяцией, на экране — «Вашим бойцом управляет бот». Флаг снят — предсказание с нового снапшота.
- **Сглаживание.** Вид рисуется в предсказанной позиции плюс смещение коррекции. При сверке к смещению прибавляется разница
  старой и новой предсказанных позиций, затем смещение экспоненциально затухает за `CorrectionSmoothingSeconds` (0,1 с).
  Если разница больше `SnapDistanceCells` (3) или это возрождение — вид ставится сразу. Внешние толчки (отброс, «Таран», крюк врага)
  приходят с опозданием и догоняются плавным смещением, без «телепорта».
- Почему крюк не предсказываем: если предсказанное подтягивание окажется промахом, бойца откатит назад до 7 клеток.
  Если ждать сервер, подтягивание начнётся на RTT позже и догонится по ходу движения — это заметно меньше.

### 2.6 Чужие бойцы: интерполяция

- В буфере лежат последние снапшоты (`NetLimits.SnapshotHistory` = 32). Позиция между двумя снапшотами вокруг `renderTick` —
  линейная интерполяция, как офлайн в `MatchViewState`; направление берётся из ближайшего.
- Если данных новее `renderTick` нет (серия потерь), позиция экстраполируется по скорости не дольше `MaxExtrapolationMs` (120 мс),
  потом боец замирает. Когда данные приходят, он плавно возвращается (за `CorrectionSmoothingSeconds`). Появление и возрождение —
  без скольжения, как сейчас.
- Боец, которого в снапшоте нет (скрыт от своей команды), в состоянии показа остаётся с `VisibleToTeams` без своей команды — виды
  прячут его, как офлайн. Позиция скрытого клиенту неизвестна и не нужна.
- Снаряды чужих передаются «сегментами» (§4.4): положение = начало + направление × скорость × (t − тик начала). Конец снаряда
  (тик и точка) приходит в снапшоте раньше, чем `renderTick` дойдёт до этого места: снаряд на экране долетает до точки конца и исчезает.
- **События** — только те, что читают виды (§4.4): `Damaged`, `Healed`, `AbilityFired` ульты, `UltReady` своего. Они уходят
  в `HitFeedback`, когда `renderTick` доходит до их тика, — число урона появляется ровно тогда, когда снаряд на экране долетел.
  Исключение — события, где `Source` — свой боец: они выдаются сразу по приходу (своё попадание ощущается на ≈ 100 мс раньше), а число
  ставится в показанную позицию цели. `TileBroken` для `MapView` выводится из блока клеток снапшота, когда до него доходит `renderTick`.

### 2.7 Свой выстрел

- Анимация и звук выстрела, сам снаряд, зона навеса и мина появляются сразу из предсказания: по событию `AbilityFired`
  на переднем крае предсказания. При пересчёте предсказания события не повторяются: клиент помнит новейший тик, события которого
  уже выданы, и при пересчёте выдаёт только более новые.
- Свой снаряд рисуется на линии предсказания. Он останавливается на стене (геометрия совпадает с сервером), на краю дальности
  или на теле **отображаемого** врага — это «мягкое» попадание без числа урона. Число урона, вспышка и звук попадания —
  только по серверному событию.
- Автоприцел решает сервер (D-007): для снарядов и навеса — по текущим позициям, для мгновенных доставок — по позициям отката
  (§2.8), а предсказанный выстрел целится в отображаемые позиции. Расхождение направления видно до прихода снапшота, после чего
  вид плавно сливается с серверным (≤ 100 мс).
- Если сервер выстрел не подтвердил (например, у него не было заряда), снаряд исчезает при сверке. Серверный `AbilityFired`
  своего уже показанного выстрела повторно не проигрывается.

### 2.8 Компенсация лага

Решение: **да** для мгновенных контактных попаданий, **нет** для снарядов и зон.
- Мгновенные попадания: конус (`MeleeCone` — лапа Бруно, когти Векса), круг вокруг себя (`SelfArea` — «Взмах» Новы, «Заварка»)
  и касание телом при рывке (`Dash` — «Таран»). Для них сервер берёт позиции **других** бойцов из истории (`MatchState.PositionHistory`:
  позиция и «жив» каждого слота в конце каждого тика, кольцо на `SimLimits.MaxRewindTicks` = 12 тиков) на `d` тиков назад, где `d` —
  `PlayerInput.ViewDelayTicks` этого ввода, урезанный пределами ниже. Клиент считает `ViewDelayTicks = round(Tpred − renderTick)` —
  такими он видел врагов в момент нажатия.
  - По тем же позициям считается и автоприцел этой доставки (выбор цели и направление): иначе направление «на текущую позицию»
    не совпадёт с проверкой «по прошлой».
  - Прошлые позиции читаются через одну функцию (`LagCompensation.TargetPosition(state, slot, d)`) только в проверках попадания и
    выборе цели; состояние не подменяется — эффекты, события, отброс и рассыпание желудей берут текущие позиции.
  - Цель, которая в окне `[T − d, T]` хоть раз была не жива (умерла, возродилась), проверяется без отката.
  - Стены и купола — по текущему состоянию.
- Игрок видит врагов с отставанием ≈ RTT + запас ввода + задержка интерполяции: ≈ 280 мс при RTT 150 мс (§2.2) и до ≈ 350 мс при
  джиттере 50 мс (условия CI, GDD §8.3). Поэтому откат ограничен `LagCompMaxRewindMs` (350 мс — покрывает цель GDD) и оценкой сервера:
  его RTT клиента + запас ввода + задержка интерполяции, о которой сообщает клиент (не больше `InterpDelayMaxMs`), + 2 тика.
  Выше предела компенсация частичная.
- Для снарядов, навеса и мин отката нет, потому что: (1) у снаряда есть время полёта 0,3–0,7 с и уворот — главный навык цели,
  а откат ломает его и даёт цели «попадание за стеной»; (2) автоприцел (основной ввод детей) решается на сервере по текущим
  позициям, ему лаг не мешает; (3) навес телеграфируется 0,5 с, и цель обязана успеть уйти. Цена отказа: при ручном прицеле
  и 150 мс упреждение нужно брать примерно на 0,7 клетки больше — на фоне 1,7 клетки упреждения, которое капле нужно на полёт.
- Компенсация выключается флагом `LagCompEnabled` — для сравнения на плейтестах.

### 2.9 Потери пакетов и плохая сеть

| Ситуация | Что происходит |
| --- | --- |
| 2 % потерь, 50 мс джиттера | Ввод не теряется (избыточность 4). Следующий снапшот приходит через 33 мс с дельтой к подтверждённой базе — интерполяция потерь не замечает |
| серия из 3–5 потерь | Экстраполяция ≤ 120 мс, затем плавное догоняние. Дыры во вводе закрывают повтор и перенос нажатий |
| ввода нет > 1,5 с | Бойцом управляет бот (§7); флаг в снапшоте выключает предсказание у клиента |
| пакетов нет > 5 с | Соединение потеряно, клиент переподключается (до 60 с) |
| RTT 250 мс и выше | Играть можно, значок пинга красный, компенсация лага урезается лимитом |

## 3. Транспорт

### 3.1 Сравнение

### 3.2 Устройство

- **Сокеты.** Интерфейс `IDatagramSocket` (отправка и приём в предвыделенные буферы).
  - Клиент: `UdpDatagramSocket` — **подключённый** UDP-сокет (`Connect`, затем `Send/Receive(byte[], …)`), под Mono и IL2CPP
    не выделяет `EndPoint`. Опрашивается без блокировки раз в кадр в главном потоке: `Available`/`Poll(0)` и перегрузки с
    `out SocketError` — в штатной работе исключений нет (они выделяют память). Адрес сервера задаётся именем хоста; имя разрешается
    заранее в фоне (`Dns.GetHostAddressesAsync` при выборе региона, результат кэшируется), никогда в кадре. Семейство сокета — по
    полученному адресу (A или AAAA): так работают и IPv6-only сети (позже — iOS). Ошибки отправки и приёма (`ConnectionReset`,
    `NetworkUnreachable` и т. п.) — сигнал «путь сломан» (см. «Смена адреса»), а не исключение для логики. LAN-обнаружение
    (широковещание, `EnableBroadcast`) и пинг регионов идут через отдельный неподключённый сокет в меню — там выделения допустимы.
  - Сервер (.NET 8+): один сокет `[::]` (dual-stack), `ReceiveFrom/SendTo(Span<byte>, SocketFlags, SocketAddress)` —
    без аллокаций; приём — неблокирующий, в игровом потоке (§5.3). Запасной `PortableUdpServerSocket` (`Arena.Net.Server`, API
    .NET Standard 2.1: `ReceiveFrom(byte[], ref EndPoint)`, выделяет память на пакет) — для bootstrap-сборки и для тестов в Unity.
    **Windows** (`RuntimeInformation.IsOSPlatform(OSPlatform.Windows)`): сразу после создания — `SIO_UDP_CONNRESET` выключить
    (`IOControl(unchecked((int)0x9800000C), new byte[4], null)`), иначе ICMP «порт недоступен» от ушедшего клиента роняет
    следующий `ReceiveFrom` с WSAECONNRESET. `ConnectionReset` и `MessageSize` (датаграмма больше буфера) считаются в метрике и
    пропускаются — цикл приёма не падает. Буфер приёма — 2048 Б: всё длиннее `MaxPacketBytes` отбрасывается.
  - Тесты: `InMemoryNetwork` на виртуальных часах — задержка, джиттер, потери (в том числе пачками, модель Гилберта–Эллиотта),
    дубли, перестановка, лимит полосы; RNG детерминированный. Тесты на настоящих сокетах слушают только `127.0.0.1` — без запросов
    брандмауэра.
- **Размер пакета.** `NetLimits.MaxPacketBytes` = 1200: минимальный MTU IPv6 (1280) минус заголовки; так делает и QUIC.
  Фрагментации нет: каждое надёжное сообщение ≤ `NetLimits.MaxReliableMessageBytes` (1000 Б). Самое большое — `MatchEnded` на 10 слотов
  (≈ 300 Б); кодер бросает исключение на превышение, тест держит запас. Понадобятся большие сообщения (этап 4) — добавить тогда.
- **Заголовок** (18 байт):

```
u8   kind (4 бита) | flags (4 бита)   ConnectRequest/Challenge/Response, Ping/Pong, Discover — без соединения; Data — с соединением
u64  connectionId                     случайные 64 бита; 0 у пакетов без соединения
u16  sequence                         номер своего пакета (по кругу)
u16  ack                              новейший полученный от собеседника
u32  ackBits                          32 предыдущих
u8   ackDelay                         задержка подтверждения, ×0,25 мс
```

  Уточнено в S3.4 (D-093): флаги — `HasReliable` (1), `HasPayload` (2), `HasAcks` (4, поля ack валидны), `Signed` (8, этап 4).
  `PathChallenge`/`PathResponse` — голый заголовок, 64 бита вызова — в полях sequence/ack/ackBits; `Disconnect` — заголовок +
  байт причины. Надёжная секция пакета: `varuint count; (u16 id, u16 смещение в кольце, varuint длина, байты)` — приёмник
  зеркалит кольцо отправителя.

- **Подтверждения** — по схеме Фидлера: ack + 32 бита. По подтверждению отправитель узнаёт, какие надёжные сообщения доставлены,
  какой снапшот стал базой, и получает образец RTT (за вычетом `ackDelay`). Отдельного подтверждения снапшотов нет: сервер помнит,
  какой снапшот ушёл в каком пакете.
- **Каналы.**
  1. Ненадёжный — полезная нагрузка пакета (ввод, снапшот, статус очереди): новое важнее старого, старые отбрасываются по номеру.
  2. Надёжный упорядоченный — сообщения управления (`MatchStart`, `MatchEnded`, `QueueJoin` и др.). Подклеиваются к любому пакету,
     повторяются по RTO = max(SRTT + 4·RTTVAR, `MinRtoMs`), окно — `NetLimits.ReliableWindow` (64 сообщения), доставка по порядку.
     Память — кольцо байт `NetLimits.ReliableBufferBytes` (8 КБ) на соединение (выделяется при подключении, не «окно × максимум»).
- **Поддержание связи.** В лобби keepalive раз в `KeepaliveSeconds` (1 с) — раньше, чем срабатывают NAT-таймауты мобильных
  операторов (бывают около 30 с). В матче трафик и так идёт 30 раз в секунду. Соединение считается потерянным через
  `DisconnectTimeoutSeconds` (5 с) без пакетов. Явный `Disconnect` отправляется 3 раза ненадёжно.
- **Рукопожатие** (до проверки адреса сервер ничего не запоминает):
  1. Клиент → `ConnectRequest {protocolId, protocolVersion, contentHash, purpose (Lobby/Match/Rejoin), nonce}`, **дополненный
     до 1200 байт**. Это защита от усиления (ответ меньше запроса) и проверка, что путь пропускает 1200 байт.
  2. Сервер → `ConnectChallenge {cookie}`, где cookie = SipHash-2-4(ключ сервера, адрес клиента ‖ nonce ‖ отрезок времени).
  3. Клиент → `ConnectResponse {cookie, nonce, purpose, token?}` — тоже 1200 байт.
  4. Сервер проверяет cookie, версии, лимиты и токен и отвечает `ConnectAccepted {connectionId, параметры: частота
     снапшотов, избыточность, лимиты}` или `ConnectRejected {reason}`. Причины: `VersionMismatch`, `ContentMismatch`,
     `ServerFull`, `Maintenance`, `RateLimited`, `InvalidToken`, `MatchOver`. Повторный `ConnectResponse` с того же адреса с тем же
     `nonce` (ответ потерялся) получает тот же `ConnectAccepted` — второго соединения не создаётся.
- **Смена адреса** (NAT-rebinding, переход Wi-Fi ↔ LTE). Пришёл пакет с известным `connectionId` с нового адреса — сервер
  отправляет туда `PathChallenge` (не больше полученного пакета) и меняет адрес, только когда клиент ответит `PathResponse`.
  Если отправка падает (Android сменил сеть, сокет привязан к старому интерфейсу), клиент пересоздаёт сокет и продолжает с тем же
  `connectionId`. Если связь пропала совсем — новое рукопожатие с токеном (§7).
- **Лимиты** (в настройках сервера): рукопожатий с одного IP в минуту (щедрый: за CGNAT мобильного оператора за одним IP бывают
  сотни игроков), пакетов и байт в секунду на соединение, размер очереди входящих пакетов матча. Превышение — тихий отброс, долгое
  превышение — `Disconnect(RateLimited)`.
- **LAN-обнаружение** (`Discover`) включается настройкой `LanDiscovery` (по умолчанию — да на ПК, нет в конфиге VPS); сервер отвечает
  только на запросы с частных адресов, запрос дополнен до размера ответа.

### 3.3 Безопасность транспорта (уровень этапа 3)

| Угроза | Мера |
| --- | --- |
| подмена адреса, чужие пакеты извне пути | cookie-рукопожатие, 64-битный случайный `connectionId`, окно повторов по номеру пакета, проверка пути при смене адреса |
| усиление (DDoS через наш сервер) | ответ на неподтверждённый адрес не больше запроса, запросы дополнены до 1200 байт |
| флуд | лимиты по IP и по соединению |
| читы через протокол | сервер принимает только ввод (§8) |
| прослушка и подмена в той же Wi-Fi (атакующий на пути) | **на этапе 3 не защищаемся.** Персональных данных и аккаунтов нет, токен живёт до конца матча, худший ущерб — «перехват бойца» в одном матче. Шифрование не мешает читам: клиент и так видит свои данные |
| этап 4 | Ключи сессии выдаёт HTTPS-бэкенд вместе с аккаунтом. Каждый пакет подписывается 8-байтным SipHash-тегом (флаг в заголовке уже зарезервирован), при необходимости — шифрование ChaCha20 (чистый C#, проверка по тест-векторам RFC 8439) |

Уровень защиты этапа 3 — D-088 (было Q-016; человек может пересмотреть).

## 4. Протокол и сериализация

### 4.1 Версии

- `NetProtocol.Version` (u16) меняется при любом изменении формата. `NetProtocol.Id` (u32) — «магия» протокола.
- `ContentHash` (u64) — первые 8 байт SHA-256 от канонической сериализации всех Defs матча: бойцы, способности, правила, карты,
  режимы, боты (§5.4). Его пишет экспортёр в заголовок пакета данных; клиент берёт его из заголовка встроенного в сборку пакета,
  сервер при загрузке пакета перепроверяет.
- Несовпадение даёт `ConnectRejected(VersionMismatch | ContentMismatch)` и экран «Обновите игру» (GDD §8.3). Один процесс
  обслуживает одну версию. При обновлении новые процессы запускаются рядом со старыми, старые доигрывают свои матчи.

### 4.2 Сообщения

| Сообщение | Канал | Направление | Содержимое |
| --- | --- | --- | --- |
| `ConnectRequest/Challenge/Response/Accepted/Rejected` | без соединения | §3.2 | |
| `Ping` / `Pong` | без соединения, с лимитом | К ↔ С | nonce, оба одного размера — замер пинга до региона |
| `Discover` / `DiscoverReply` | широковещательно в LAN | К → сеть | версия, хэш данных, ключ имени сервера, занятость, техработы; запрос дополнен до размера ответа, на VPS выключено (§3.2) |
| `QueueJoin` | надёжный | К → С | режим, боец (сервер проверяет режим и индекс бойца) |
| `QueueStatus` | ненадёжный (важен новейший) | С → К | состояние, секунды ожидания, «найдено N из M» |
| `QueueCancel` | надёжный | К → С | |
| `QueueRejected` | надёжный | С → К | причина: неверный режим или боец, техработы, соединение уже в матче (добавлено в S3.8, D-098) |
| `MatchAssigned` | надёжный | С → К | `matchId`, адрес (пусто — этот же сервер), `rejoinToken` (128 бит), слот |

Сид матча клиенту не передаётся. Начало боя — по тикам снапшотов (§2.3) |
| `ClientReady` | надёжный | К → С | сцена загружена |
| `Input` | ненадёжный, 30 Гц | К → С | §2.4 + флаги (например, просьба о ключевом кадре) + раз в секунду статистика клиента (ошибки предсказания, недоборы интерполяции, задержка интерполяции) |
| `Snapshot` | ненадёжный, 30 Гц | С → К | §4.4 |
| `MatchEnded` | надёжный | С → К | победитель или места, статистика слотов, MVP, тик конца |
| `Eliminated` | надёжный | С → К | «Последний зверь»: место и статистика своего слота — личный итог выбывшего (§7) |
| `Leave` | надёжный | К → С | игрок вышел сам — бот сразу |
| `ServerNotice` | надёжный | С → К | техработы, выключение сервера |
| `PathChallenge` / `PathResponse` | ненадёжный | §3.2 | |

### 4.3 Упаковка и квантование

- `BitWriter` и `BitReader` работают над предвыделенным `byte[]` (little-endian, без аллокаций). Тики и счётчики пишутся как
  varint (тики — zigzag: бывают в прошлом, в будущем и отрицательные — отсчёт), «не изменилось» — одним битом. Шаги квантования
  и ширины полей — именованные константы `NetProtocol` (технические, как `SimLimits`, D-004).

| Величина | Формат | Точность |
| --- | --- | --- |
| позиция чужого бойца, подбора, зоны, начала снаряда | 2 × u16 на диапазон карты (до 64 клеток) | 1/1024 клетки |
| позиция, направления, скорости **своего** бойца | float32 как есть | точно (база для пересчёта) |
| направление взгляда чужого | u8, угол | 1,4° |
| направление чужого снаряда | u16, угол | ≈ 0,005° (только для видов) |
| прицел (ввод) | 2 × int16 | 1/32767, без тригонометрии (§2.4) |
| движение (ввод) | 2 × int8 | 1/127 |
| HP, макс. HP | u16 (varint-дельта) | точно |
| заряды атаки, применения трюка | столько бит, сколько нужно для `MaxCharges` / `TrickUses` из правил | точно |
| заряд ульты | своему — varint, чужим — 1 бит «готова» | точно |
| тики | zigzag-varint от тика снапшота | точно |
| радиус зоны | u8 × 1/32 | ≈ 0,03 клетки |

- Квантованные значения на клиенте идут только в виды (и для чужих — в теневое состояние). Состояние своего бойца — точное.

### 4.4 Снапшот

Снапшот собирается для каждого клиента отдельно (команда `k`, слот `s`):
1. **Заголовок:** `serverTick`, флаг ключевого кадра (иначе — `baselineTick`; «база 0» как признак ключевого кадра не годится —
   тик 0 настоящий), `lastAppliedInputTick(s)`, `InputMarginMin(s)` (§2.3), флаг «своим бойцом управляет бот» (§7).
2. **Режим:** фаза (в том числе отсчёт до старта, §2.3), отсчёт удержания (команда и тик конца), конец и победитель, счёт желудей
   команд (`ModeState`, S3.5 — скрытый носитель в снапшот не попадает, и сумма по бойцам была бы неверной). Для «Последнего зверя» —
   шаг и границы тумана, число живых.
3. **Свой боец:** **все поля `FighterState`**, точно (дельта по полям к базе с маской полей), плюс свои статусы (вид, значение,
   тик конца). Что каждое поле передаётся, проверяет тест рефлексией (как `StateEqualityTests`).
4. **Остальные бойцы** — те, кого видит команда k (`VisibleToTeams`), а в режимах с AOI — ещё и в радиусе `AoiRadiusCells`
   от своего бойца: активен/жив, позиция, взгляд, скорость (для экстраполяции), HP и макс. HP, заряды, флаги (в кусте,
   невидим — только для союзника, его рисуем полупрозрачным; для союзника ещё «его видит чужая команда» — для той же
   полупрозрачности; оглушён, замедлен, рывок, помечен моей командой, ульта готова), жёлуди или ягоды. Союзники видны всегда.
   Статика слота (боец, команда, уровень) уже есть в `MatchStart`.
5. **Снаряды — сегментами:** слот, `SpawnTick` (идентичность снаряда: отскок и новый снаряд в том же слоте различаются по нему),
   владелец, способность, тик начала сегмента, точка начала, направление, оставшиеся пробития и отскоки, маска уже задетых бойцов
   (10 бит), флаг «сегмент после отскока» (дальность — `BounceRange`). Положение клиент считает сам; из этих же полей собираются свои
   снаряды тени (§2.5). После отскока начинается новый сегмент. **Конец** снаряда: слот, тик и точка конца (u16 × 2). В AOI-режимах —
   только снаряды в радиусе `AoiRadiusCells`. Снаряды видны все: выстрел раскрывает стрелка (D-024).
6. **Зоны,** видимые команде k (мины — по D-030): вид, способность, владелец, команда, точка, начало дуги, радиус, тики появления,
   срабатывания и конца, флаг «сработала».
7. **Подборы** (жёлуди, ягоды): вид, ценность, точка, тик доступности, `SpawnTick` (виды узнают по нему переиспользованный слот).
8. **Клетки:** изменения с базового тика — индексы сломанных стен и ящиков. В ключевом кадре — битовая маска отличий от карты.
9. **События** — только те, что читают виды: `Damaged`, `Healed`, `AbilityFired` ульты (звук), `UltReady` (только своему). Каждое
   уходит в снапшотах своего тика и следующих — всего `EventRedundancyTicks` (3) раз; клиент отбрасывает уже принятые тики. Сжатие:
   тип — 5 бит, источник и цель — 4 + 4 бита, значение — varint, точка — u16 × 2, способность — u8. Фильтр строже, чем «видит цель
   или источник»: событие уходит команде k с точкой, если k видит **цель**; если цель скрыта от k, событие получает только клиент
   источника — без точки и без слота цели, только для звука и вибрации, как офлайн (`HitFeedback` и так не показывает число по скрытой
   цели). Иначе союзник выстрелом в куст узнавал бы точку спрятавшегося врага. `AbilityFired` ульты — если k видит источник. Лимит —
   `MaxEventsPerSnapshot`, новые важнее старых.

Остальные правила снапшотов:
- **Дельта.** Сервер хранит для каждого клиента кольцо отправленных «видов» (`NetLimits.SnapshotHistory` = 32, ≈ 1 с). База —
  новейший подтверждённый вид; если подходящего нет — уходит ключевой кадр. Клиент хранит такое же кольцо принятых. Вид — это
  ровно то, что восстановит клиент (база + вошедшие в снапшот изменения), а не истинное состояние, — иначе дельта от неполного
  снапшота разойдётся. Вид хранит компактные списки активных сущностей, а не полные массивы по `SimLimits`.
- **Порядок и дубли.** Показывается только снапшот новее самого нового из полученных; опоздавший, если декодируется, всё равно
  кладётся в кольцо баз (транспорт его подтвердил — сервер может выбрать его базой). Нет базы — снапшот отбрасывается, во вводе
  ставится просьба о ключевом кадре.
- **Лимит 1200 байт.** Части идут по приоритету: заголовок и режим → свой боец → союзники → враги по расстоянию → снаряды
  по расстоянию → зоны → подборы → клетки → события. Что не влезло, остаётся с прежней базой и уходит в следующем снапшоте.
  Признаки присутствия (исчез боец, кончился снаряд) идут вместе со своим блоком и не отбрасываются.
  Ожидаемый ключевой кадр: 3×3 — 400–800 Б, королевская битва — 600–1100 Б.
  **Измерено в S3.5 (D-094):** ключевой кадр 3×3 — до ≈ 360 Б, «Последний зверь» (AOI 16) — до ≈ 230 Б; клетки и в ключевом
  кадре идут списком номеров (разности varint), а не битовой маской — сломанных клеток мало.
- **Фильтр** работает на сервере до кодирования: невидимое команде в пакет не попадает вовсе, а не просто «маскируется».
  Это и античит против «видения сквозь кусты».

### 4.5 Бюджет трафика

Оценка для 3×3 в бою, с дельтой:

| Часть | Байт |
| --- | --- |
| IPv4 + UDP | 28 |
| заголовок транспорта | 18 |
| заголовок снапшота и режим | ≈ 10 |
| свой боец (позиция, взгляд, прогресс заряда) | ≈ 16–20 |
| 5 бойцов в движении | ≈ 40 |
| новые сегменты снарядов (2–4 × 12) и концы (× 5) | ≈ 25–55 |
| события (1–3 за тик × 3 копии × ≈ 6) | ≈ 18–54 |
| **итого** | **≈ 155–225 → ≈ 4,7–6,8 КБ/с вниз** при 30 Гц. Пики (ульта Пикса — 10 капель) ≈ 350 Б, то есть кратко ≈ 10 КБ/с |

Вверх: 28 + 18 + ≈ 27 (4 ввода и служебные поля) ≈ 73 Б × 30 = **≈ 2,2 КБ/с**. Матч 2:30 — это ≈ 1,2–1,6 МБ мобильного трафика.
Лимит GDD в 10 КБ/с в среднем выполняется с запасом (пики короче секунды). Это проверяют тест бюджета на полном бот-матче
(S3.5, S3.14) и метрика сервера.
Если не уложимся — снапшоты 20 или 15 Гц (`SnapshotRateDivisor`) и AOI.

**Уточнено измерением (S3.5, D-094):** полезная нагрузка снапшота на полных бот-матчах при подтверждении через 5 тиков —
«Жёлуди» 3×3 в среднем ≈ 81 Б (максимум ≈ 360 Б), «Последний зверь» 10 бойцов ≈ 50 Б (максимум ≈ 230 Б). С заголовками
(18 + 28 Б) это ≈ 127 Б × 30 ≈ **3,8 КБ/с вниз** для 3×3 — меньше оценки выше: неизменные поля стоят 1 бит. Бой живых игроков
активнее ботов «Новичок» — метрика сервера (S3.9) и тест S3.14 перепроверят.

### 4.6 Ноль аллокаций

- Все буферы пакетов, кольца снапшотов, вводов и событий предвыделены по `NetLimits`. Кодеры пишут в `Span`/`byte[]`, строк
  в горячем пути нет: логи — счётчики и одна строка раз в 10 с.
- Клиент использует подключённый сокет (`Receive` без `EndPoint`) и опрос без потоков, сервер — API `SocketAddress` из .NET 8+.
- Проверка: `AllocationAssert` (EditMode) для кодеров, транспорта, `MatchHost.Tick` и клиентской сверки; на сервере —
  `GC.GetAllocatedBytesForCurrentThread` в self-test. Строго — только в сборке .NET 8+: в bootstrap-сборке приём через `EndPoint`
  выделяет память на пакет (допустимо для разработки и малой нагрузки) — self-test печатает число, но не падает.
- Клиентский `UdpDatagramSocket` проверяется `AllocationAssert` на loopback в EditMode (Mono). Если Mono всё же выделяет в
  `Send/Receive` — записать в Decisions и мерить на телефоне (IL2CPP), логику не менять.

### 5.3 Процесс

- Один процесс — это узел: лобби + N матчей на одном UDP-порту (`UdpPort`, 7777). Локальный HTTP — только для метрик
  (`MetricsPort`, 7778, по умолчанию на 127.0.0.1).
- **Потоки этапа 3 — один игровой поток** (`ServerNode.Update(now)`): неблокирующий приём всех пришедших датаграмм
  (`ReceiveFrom` до «пусто») → разбор заголовка → по `connectionId` в лобби или матч → тики всех матчей, у которых наступил срок →
  отправка (`SendTo` из того же потока). Ожидание до ближайшего срока — `Socket.Poll` с таймаутом (проснётся и от пакета). Плюс поток
  метрик (HTTP): игровой поток раз в секунду публикует снимок счётчиков под `lock`, HTTP читает только снимок. По оценке §5.7 один
  поток держит ≈ 100 матчей — это цель нагрузочного теста S3.15; этапу 3 нужно 1–10.
- `WorkerThreads` > 1 — только если S3.15 покажет p99 тика выше бюджета: тогда матч закрепляется за рабочим потоком, приём уходит
  в отдельный поток с SPSC-кольцами на рабочего, таблица соединений становится потокобезопасной. Заранее этого не делаем:
  многопоточность — главный источник тонких ошибок, а логика (`MatchHost`, `Matchmaker`) и так однопоточная и под тестами.
- **Тик-луп:** срок тика матча `n` = старт + n × 33,333 мс (считается от номера — ошибка не копится). На Windows при старте —
  `timeBeginPeriod(1)` (winmm, действует только на процесс; без него `Thread.Sleep` и таймауты спят до 15,6 мс), при выходе —
  `timeEndPeriod(1)`. Если отставание больше `MaxCatchUpTicks`, тики пропускаются, а пропуск попадает в метрику — защита от «спирали».
  Self-test меряет джиттер тика (p99 < 2 мс). **Windows 11** игнорирует `timeBeginPeriod` у процесса без видимого окна (служба,
  скрытая консоль) — сначала `SetProcessInformation(ProcessPowerThrottling, …IGNORE_TIMER_RESOLUTION)`; `Socket.Poll` с таймаутом
  спит шагами системного таймера, поэтому ожидание — `Sleep(1)` с `Poll(0)` между снами и короткий спин перед сроком (D-099).
- `MatchHost.Tick(now)` — логика из `Arena.Net.Server`, одинаковая в тестах и на сервере: входящие пакеты → вводы слотов (§2.4) →
  ввод ботов (`BotController` для слотов ботов и подменённых) → `MatchSimulation.Tick` → события в журналы клиентов (с фильтром) →
  снапшоты по расписанию → проверки времени (таймауты, AFK, конец).
- **Жизненный цикл матча:** `Assembling` (лобби собрало состав) → `Joining` (ждём подключений до `JoinTimeoutSeconds`,
  кто не пришёл — бот) → `Loading` (`MatchStart`, ждём `ClientReady` до `LoadTimeoutSeconds`; не пришёл — бот) → `Countdown`
  (`CountdownSeconds`, 3 с: тики от `−CountdownTicks` до −1, снапшоты и ввод уже идут, симуляция стоит, §2.3) → `Running` (с `T = 0`
  каждый тик — `MatchSimulation.Tick`) → `Ended` (`MatchEnded`, итог в лог, матч держится `ResultLingerSeconds` для
  возвращающихся) → удаление.
  Отправка итога в бэкенд — на этапе 4, через тот же интерфейс `IMatchResultSink`; на этапе 3 итог только пишется в лог.
- Сид матча — криптослучайный. Журнал ввода (все слоты, все тики) пишется по флагу `RecordInputLog`, в тестах — всегда.
  `ReplayVerifier` прогоняет `MatchSimulation` по журналу и сравнивает `ContentEquals`.
- **Остановка** (SIGTERM — `PosixSignalRegistration`, Ctrl+C — `Console.CancelKeyPress`): новые матчи не принимаются (`ServerNotice`),
  текущие доигрываются до `DrainSeconds` (180), затем процесс выходит. В Docker `stop_grace_period` — не меньше 180 с. Сигнал — тонкая
  обвязка над `ShutdownHandler.RequestStop()`; self-test вызывает тот же метод.
- **Техработы:** файл-флаг `maintenance.flag` рядом с конфигом или настройка. Тогда `QueueJoin` получает отказ `Maintenance`,
  а идущие матчи доигрываются.

### 5.4 Данные на сервере: пакет данных

- Читать ScriptableObject сервер не умеет. Editor-метод `Arena.Editor.Net.ContentPackExporter.Export` строит Defs через
  `ConfigConverter` (те же, что офлайн) и пишет их **канонической двоичной** сериализацией (`ContentPackWriter` из `Arena.Net`,
  фиксированный порядок полей, float — побитово) в один файл `Assets/_Project/Data/Net/ArenaContent.bytes` (TextAsset, в git вместе
  с `.meta`). Заголовок пакета: магия, версия формата, `ContentHash` — первые 8 байт SHA-256 от остальных байт.
- `ContentPackReader` читает пакет в `ContentBundle`: правила, бойцы, карты, режимы, боты, политика матча (уровень,
  `UnlockAllAbilities`). `ContentBundle.CreateMatchDefs(карта, режим)` — одна функция для сервера и онлайн-клиента.
- Сервер получает копию файла при сборке (`server-build.ps1`; в csproj — `None Include … CopyToOutputDirectory`) и при загрузке
  перепроверяет хэш. **Онлайн-клиент строит Defs матча из того же файла** (ссылка из `NetConfig`), а не из SO: Defs совпадают с
  серверными бит в бит (на телефоне `ConfigConverter` с float-арифметикой IL2CPP мог бы дать другие биты, и хэш не сошёлся бы
  навсегда); хэш берётся из заголовка, SHA-256 на телефоне не нужен. Офлайн по-прежнему строит Defs из SO. Порядок бойцов в пакете =
  порядок `GameDatabase.Fighters` (`MatchRunner` выбирает виды снарядов по индексу).
- **Тест-сторож:** экспорт в памяти из текущих SO совпадает с закоммиченным файлом, иначе «забыли переэкспортировать после сидера».
  Чтение → запись даёт те же байты. Defs после чтения ведут себя как исходные: короткий матч даёт тот же хэш состояния. Тест
  рефлексией: каждое поле каждого Def-класса проходит через запись и чтение (новое поле без записи роняет тест).
- `DataSeeder.SeedAll` в конце сам вызывает экспорт, поэтому в рабочем цикле шага ничего не меняется: `ViewAssetBuilder` →
  `DataSeeder` (+ экспорт пакета).

### 5.6 Мониторинг и логи

- **Метрики:** `GET /metrics` в текстовом формате Prometheus и `GET /healthz`. Мини-HTTP — свой, на `TcpListener`, без ASP.NET,
  поэтому работает и в bootstrap-сборке. Что считаем:
  - матчи, игроки, боты; очередь (медиана и p90 ожидания, доля матчей с добором ботами);
  - время тика (среднее, p99, максимум), джиттер срока тика и отставания;
  - байты и пакеты в секунду на вход и выход, размер снапшота (среднее, p99), число ключевых кадров;
  - потери по соединениям, гистограмма RTT, поздние и пропущенные вводы, перенесённые нажатия;
  - подмены ботом, переподключения, отказы по причинам, срабатывания лимитов;
  - поправки предсказания (из статистики клиентов) и отброшенное по ёмкостям (`Dropped*`).
- **Логи:** строки в stdout (удобно для Docker), уровень — из конфига. Раз в 10 с — одна строка-сводка, ошибки — с `matchId`.
  Итог матча — строка JSON в `logs/matches.jsonl`: режим, карта, длительность, победитель, бойцы и статистика слотов,
  кто бот и кто человек, корзина RTT — без идентификаторов игроков и IP.
- IP в логи не пишутся, только счётчики; для отладки есть `connectionId`.
- Prometheus и Grafana в docker-compose — по желанию (бесплатно), не обязательны. Оповещения о сбоях (GDD §8.3) — после выбора
  хостинга: нужен канал уведомлений, его выбирает человек (Q-014); до того — автоперезапуск (systemd, Docker) и логи.

### 5.7 Ёмкость (оценка)

- CPU на матч 3×3: ≈ 0,12 мс/с симуляции + ≈ 3 мс/с на снапшоты и кодирование + ≈ 2–4 мс/с системных вызовов
  (≈ 360 пакетов/с) — итого ≈ 6–7 мс CPU в секунду, то есть **≈ 150 матчей на ядро**. Память — ≈ 1–2 МБ на матч (кольца видов:
  6 клиентов × 32; компактные списки сущностей, §4.4, сокращают это в разы), журнал ввода по флагу — ещё ≈ 1 МБ на 2,5 мин.
- Сеть: матч — ≈ 6 × 7 КБ/с ≈ 42 КБ/с вниз; 100 матчей — ≈ 34 Мбит/с.
- Этапу 3 нужно 1–10 матчей. Нагрузочный тест — 100 матчей на ПК (S3.15), 500 — перед софт-запуском (GDD §8.3).

## 6. Матчмейкинг и лобби

### 6.1 Где и как

- Сервис `Matchmaker` (чистый C#, `Arena.Net.Server`) живёт в том же процессе и на том же UDP-порту. Клиент подключается
  (`purpose = Lobby`), отправляет `QueueJoin`, раз в секунду получает `QueueStatus`, а затем `MatchAssigned`. Соединение лобби
  сразу становится соединением матча (`MatchStart`) — переподключаться не нужно. Поле «адрес» в `MatchAssigned` оставляет
  путь к отдельным игровым узлам в будущем.
- Почему не HTTP: один порт и один протокол — проще брандмауэр, LAN и Docker; весь путь проверяется в EditMode от начала до конца;
  не нужны ASP.NET и сертификаты. HTTPS понадобится бэкенду аккаунтов на этапе 4.
- Готовые решения — Nakama (Apache-2.0), Open Match — для этапа 3 избыточны (базы данных, Kubernetes). Nakama — кандидат
  на этап 4 (аккаунты, хранилище), сравнить его нужно там.

### 6.2 Очередь и комнаты

- Очередь своя на каждый режим (`Acorns` 3×3, `LastBeast` на 10) и на каждый узел: регион = узел.
- **Сборка:** FIFO. Набралось `TeamSize × Teams` людей — матч собран. Если старейший билет ждёт `BotFillSeconds` (15 с, GDD §7) —
  матч собирается из тех, кто есть, остальные места занимают боты. Правило «до 300 кубков — 8 с», подбор по кубкам и
  выравнивание сумм кубков (GDD §8.2) включатся на этапе 4, когда появятся кубки; значение в конфиге уже есть.
- **Команды 3×3:** ботов поровну между командами (GDD §7), значит и людей тоже. 1 человек → он + 2 бота против 3 ботов;
  2 → по одному в команде; 3 → 2 + 1; 4 → 2 + 2; 5 → 3 + 2.
- **Одинаковые бойцы:** лобби старается развести одинаковых бойцов по разным командам. Если не получается — это разрешено,
  симуляция позволяет (D-087). Боты получают случайных бойцов без повторов в команде по сиду. Состав (слоты, команды, точки
  появления, бойцы ботов) собирает чистый `Core/Defs/MatchSetupBuilder` (S3.6); офлайн-`MatchSetupFactory` вызывает его же.
- Сложность ботов при доборе — `FillBotDifficulty` («Новичок»: по GDD §7 он для первых 30 кубков, а кубков пока у всех 0).
  Подмена вылетевшего — той же сложности.
- Отмена — `QueueCancel`; при обрыве связи в очереди билет удаляется через `DisconnectTimeoutSeconds`.
- `QueueStatus` даёт время ожидания и «найдено N из M» для экрана поиска (§12.4). Дети не ждут дольше 15 с — добор это гарантирует.

### 6.3 Регион и пинг

- Список регионов лежит в `NetConfig`: ключ названия, хост, порт. Первым идёт «Локальный (LAN)» — через `Discover`.
- Перед поиском клиент шлёт по 5 `Ping` в каждый регион параллельно, берёт медиану и выбирает регион с меньшей.
  В меню видны регион и пинг. В бою — значок: зелёный до 100 мс, жёлтый до 250, красный от 250 (GDD §8.2).
- Адрес вручную не вводится (GDD: никакого ввода текста), внешних ссылок нет. Адреса серверов зашиты в сборку
  (`NetConfig`; список регионов пишет `DataSeeder`, его правит разработчик). Если роутер режет широковещание, IP ПК в LAN
  разработчик прописывает в сидере до сборки APK.

### 6.4 Анонимность

- Постоянного идентификатора нет (ни своего, ни устройства, ни рекламного): сервер знает только соединение — `connectionId` и адрес
  в памяти, адрес в логи не пишется. Один билет в очереди — на соединение.
- Возврат после перезапуска приложения — по `rejoinToken` из `RejoinStore` (PlayerPrefs: matchId, адрес, токен, срок; запись удаляется
  по концу матча или сроку). Токен случайный, живёт до конца матча и ничего не говорит о человеке.
- Имён, ников и чата нет — на экране только бойцы. Итог матча в логе — без адресов и идентификаторов. Окончательно проверяет юрист
  (GDD §2, §13). (Рецензия убрала `InstallId`/`installKey` из первой версии ТЗ: он был не нужен ни для очереди, ни для возврата, D-086.)

## 7. Переподключение, вылет, AFK

| Событие | Сервер | Клиент |
| --- | --- | --- |
| нет ввода `BotTakeoverSeconds` (1,5 с) | слот переходит к боту (`BotController.SetBotActive(slot, true)`): мозг с нуля, сид = матч + слот + номер подмены; в снапшотах слота — флаг «бойцом управляет бот» | если связь жива — предсказание выключено, «Вашим бойцом управляет бот» (§2.5) |
| нет пакетов `DisconnectTimeoutSeconds` (5 с) | соединение закрывается, слот остаётся у бота, `rejoinToken` действует до конца матча | экран «Связь потеряна — переподключаемся… N с», попытки по графику `ReconnectRetrySeconds` в течение `ReconnectWindowSeconds` (60 с, GDD §8.3) |
| возврат | рукопожатие `purpose = Rejoin` с токеном (адрес может быть новым) → повтор `MatchStart` и ключевой кадр. Бот снимается со следующего тика, ввод игрока снова действует | сброс предсказания и интерполяции; сцена Match остаётся или загружается заново |

| матч кончился без игрока | `MatchEnded` хранится `ResultLingerSeconds`; вернувшийся получает итог | экран итогов |
| AFK: подключён, но ввод нулевой (стики не тронуты, кнопок нет) `AfkSeconds` (30 с) | бот; любое движение или нажатие возвращает управление в том же тике. В итоге матча ставится флаг AFK — для наград этапа 4 | как при подмене ботом |
| приложение свёрнуто | ввода нет → бот через 1,5 с; если соединение умрёт — возврат по токену | `OnApplicationPause`: остановить отправку, при возвращении проверить связь, большой `dt` не догонять (прыжок часов) |
| «Последний зверь»: игрок выбыл | слот выбывает (бот не нужен), клиенту — `Eliminated` (место, статистика); соединение остаётся для «Ещё раз» | личный экран итога «N-е место», «Ещё раз» / «Меню» |
| игрок вышел сам (`Leave`) | бот сразу | — |

`BotController` нужно научить включать и выключать бота на слоте без аллокаций (сейчас есть только `AddBot`; он уже собирает мозг
заново без выделений) и сбрасывать его память (`EnemyMemory`, «видит с тика»).

## 8. Античит в пределах разумного

- Клиент шлёт только ввод. HP, урон, попадания, победы и итог считает сервер (GDD §4).
- `PlayerInput.Sanitized()` (уже есть) и квантование задают диапазоны, неизвестные биты отбрасываются.
- Ввод принимается только в окне тиков `[T, T + MaxInputAheadTicks]`, у опоздавших переносятся только нажатия. Один ввод
  на тик, а время считает сервер — «спидхак» бесполезен.
- Заряды, откаты, применения трюка, дальность, скорость и стены проверяет сама симуляция (уже есть), клиент их не обойдёт.
- Автоприцел работает на сервере (D-007). Бот ручного прицела полностью не отсечь: собираем статистику меткости по слотам,
  разбор — после MVP.
- **Видимость:** то, что команда не видит (кусты, невидимость, вне AOI, скрытые мины), не отправляется вовсе, события
  фильтруются. Модификацией клиента «увидеть сквозь кусты» нельзя.
- Компенсация лага ограничена (`LagCompMaxRewindMs` + оценка сервера), завышенный `ViewDelayTicks` выгоды не даёт.
- Лимиты пакетов, байт и рукопожатий. Повторы пакетов отсекает окно номеров, чужие `connectionId` — cookie и 64 случайных бита.
- Версия протокола и хэш данных: подмена данных в клиенте на сервер не влияет — он считает по своим.
- Журнал ввода матча (по флагу) — для разбора жалоб и багов.
- Чего нет на этом этапе: защиты памяти клиента, обфускации, сигнатур читов.

## 9. Режим «Последний зверь»

### 9.1 Правила (GDD §5.4) и уточнения

- 10 бойцов, каждый сам за себя: команда = слот (`SimLimits.MaxTeams` = 10, маски команд — уже `uint`).
- Карта 45×45 (2025 клеток ≤ `MaxMapCells` = 2048), 10 точек появления (новый символ `S` — общий спавн, в `MapConverter`;
  проверка режима — ровно 10 общих спавнов, центральная симметрия не обязательна), возрождения нет. Карта — строки в `DataSeeder`,
  как «Поляна»: удобно нарисовать четверть и отразить по двум осям (по аналогии с `MirrorBottomHalf`). Слоты получают спавны
  в порядке перестановки по сиду матча (`MatchSetupBuilder`).
- **Ящики с ягодами.** Тайл `BerryBox` уже есть (символ `$`, блокирует движение и снаряды). Прочность и урон по ящику —
  новые данные.
- **Ягода:** +8 % урона и +8 % макс. HP — аддитивно к базе уровня, множитель `1 + 0,08 × ягоды`. При подборе текущее HP
  растёт на прибавку макс. HP. Выбывший роняет все свои ягоды и ещё одну.
- **Туман:** с 0:40 безопасный квадрат сжимается на 2 клетки с каждой стороны каждые 20 с. Урон в тумане — 500/с и растёт
  на `FogDamageGrowthPerStep` (PROTO) за шаг; наносится импульсами каждые `FogPulseTicks` (PROTO 0,5 с, то есть 250 за импульс).
  Боец в тумане, если центр его тела вне квадрата. Урон наносит среда (`Source = −1`), заряда ульты он не даёт.
  Минимальный размер квадрата — `FogMinHalfSize` (PROTO 2,5).
- **Места.** Выбывший получает место = число живых до этого тика; выбывшие в одном тике делят место. Остался один —
  1-е место и конец матча. Если все последние выбыли в одном тике, победитель — тот, кто нанёс больше урона, затем меньший слот
  (детерминированно). Страховочный предел `MaxDurationTicks` (PROTO 6 мин): победитель по HP, затем по урону.
- Кубки за место начисляются на этапе 4 (место уже есть в итоге).

### 9.2 Состояние и системы

- **Core:**
  - `ModeKind.LastBeast = 2`, `LastBeastModeDef` (все числа выше) — из SO `LastBeastModeConfig` (`Data/Modes/LastBeast.asset`, сидер).
  - `ModeState`: шаг тумана, тик следующего шага, текущие границы, число живых.
  - `BoxState[] Boxes` (`SimLimits.MaxBoxes` = 64: клетка, прочность) — ящик как сущность поверх тайла. Урон по ящику наносят
    снаряд, остановленный его клеткой, а также конус, круг или взрыв, задевшие клетку: эффект `Damage` по врагу бьёт и ящик
    (PROTO: значение эффекта с уровнем и ягодами). Весь урон по ящикам — через один помощник (`BoxSystem.DamageCell`,
    `BoxSystem.DamageCircle`), который зовут доставки; в «Жёлудях» ящиков нет, и он ничего не делает. Прочность 0 → тайл становится
    `Floor` (событие `TileBroken`, как у стены) и появляется подбор-ягода. `Boxes` — в `CopyFrom`, `ContentEquals`, `Clear` и
    `StateEqualityTests`.
  - `PickupState.Kind` (`PickupKind`: `Acorn` = 0, `Berry`); жёлуди не меняются.
  - `FighterState.Berries`; урон умножается на множитель ягод в `DamageEffect` (после таланта), `MaxHealth` пересчитывается при подборе.
  - Возрождение выключает флаг `MatchDefs.NoRespawn` (по умолчанию `false` — во всех нынешних Defs и тестах возрождение остаётся;
    флаг «включено» по умолчанию `false` выключил бы его везде). `FighterStats.Place` (0 — ещё играет).
  - `LastBeastRules.Reset/Run` — рядом с `AcornsRules` (шаг 8a), `OnDefeat` вызывается из `DamageSystem.Defeat`.
  - Правило по умолчанию (§1.3) действует для всех новых полей: 0 / false — нынешнее поведение «Жёлудей».
- **Боты** (`Arena.Bots`): новые действия `FleeFog` (боец в тумане или туман дойдёт до него за N с → идти к центру безопасной зоны,
  высший приоритет), `BreakBox` (ближайший ящик, если врагов не видно), `CollectBerry` (вместо желудей). «Держаться команды»
  выключено, враг — любой другой боец.
- **Виды:** граница тумана (полупрозрачные квады), ящики (префаб), ягоды. Камера следует по обеим осям (`CameraConfig`, без
  поворота на 180°). HUD: «Осталось N», таймер шага тумана, ягоды.
- **Сеть:** ящики идут изменениями клеток, ягоды — подборами, туман — в блоке режима. AOI `AoiRadiusCells` (16): чужие бойцы
  и снаряды дальше экрана в королевской битве не отправляются. Выбывшему — `Eliminated` (§7).
- **Офлайн:** в «Тренировке» можно выбрать режим (1 человек + 9 ботов) — режим проверяется и без сервера.
- Числа, которых нет в GDD (прочность ящика, рост урона тумана, минимальная зона, разброс ягод, число ящиков) — PROTO (§13, D-089):
  S3.3 пишет их в таблицу PROTO в `Decisions.md`, человек проверяет после игры.

## 10. Развёртывание (бесплатно)

Агент не создаёт аккаунты, не пробрасывает порты на роутере и не меняет правила брандмауэра — всё это делает человек (Q-014).

### 10.1 ПК в локальной сети (первый шаг, бесплатно)

1. Однократно установить .NET 10 SDK: `winget install Microsoft.DotNet.SDK.10` (Q-012). Без него работает bootstrap-сборка
   из Unity (§5.2) — для LAN этого достаточно.
2. Запустить `Tools\server-build.ps1`, затем `Tools\server-run.ps1` (порт 7777/UDP).
3. Открыть порт в брандмауэре Windows (PowerShell от администратора):
   `New-NetFirewallRule -DisplayName "Arena server" -Direction Inbound -Protocol UDP -LocalPort 7777 -Action Allow -Profile Private`.
   Сеть Wi-Fi должна быть «Частной».
4. Телефоны в той же Wi-Fi: «Играть» → регион «Локальный» (сервер находится через `Discover`). Если роутер режет широковещательные
   пакеты — до сборки APK прописать IP ПК в списке регионов в `DataSeeder` (§6.3).
5. Пинг 150 мс в LAN даёт dev-симулятор сети: в клиенте — настройки `NetConfig` (только Development-сборки), на сервере —
   `DevNetworkConditions` в `server.json`.

### 10.2 Интернет с домашнего ПК

Пробросить UDP 7777 на роутере и подключаться по внешнему IP. Минусы: динамический IP, у провайдера часто CGNAT, риски для
домашней сети. Подходит только для коротких тестов.

### 10.3 Бесплатный облачный VPS

Условия ниже — по памяти, перед выбором их надо проверить.

Минусы: регистрация с картой, ёмкости A1 в популярных регионах часто нет, простаивающие инстансы могут забрать, доступность для страны и карты пользователя |
| Google Cloud Free Tier | e2-micro (≈ 0,25–2 vCPU, 1 ГБ) только в трёх регионах США, 1 ГБ исходящего трафика в месяц | только опыты: 1 ГБ ≈ 100 матчей |
| AWS / Azure | кредиты и пробные периоды на 6–12 месяцев | не «навсегда» |

**Инструкция для Oracle (делает человек):**
1. Зарегистрироваться и создать VM `VM.Standard.A1.Flex` (Ubuntu 24.04, 1–2 OCPU, 6–12 ГБ) в регионе ближе к тестерам.
2. В Security List разрешить входящие UDP 7777 (и TCP 22 для SSH); на самой VM — `ufw allow 7777/udp`.
3. Установить .NET runtime 8 или 10 (через `apt` или скрипт Microsoft) **или** Docker. Bootstrap-сборка тоже запустится на нём
   (`rollForward: Major`, §5.2), если SDK на ПК так и не появился.
4. Скопировать `Builds/Server/` (портативная публикация или bootstrap-сборка с пакетом данных и `config/`) или собрать образ.
   В `server.json` на VPS — `LanDiscovery: false`.
5. Включить systemd-сервис `Server/deploy/arena-server.service` (перезапускает сервер при падении).
6. Прописать адрес в списке регионов (`DataSeeder` → `NetConfig.Regions`) и собрать APK.

## 11. Тестирование без людей

### 11.1 EditMode (Unity, основное)

Виртуальные часы и `InMemoryNetwork`: сервер (`MatchHost`, `Matchmaker`) и клиенты (`NetClient`) работают в одном процессе.
Всё детерминировано (сиды сети и матча), поэтому упавший тест повторяется один в один. Кадры клиентов идут с частотой 60 Гц
с детерминированным разбросом длительности (как на телефоне), тики клиента — по его часам предсказания, а не по кадрам сервера.

- **Сериализация:** битовая упаковка, квантование (границы ошибки), varint. Фаззинг декодеров: случайные и обрезанные пакеты
  не дают ни исключений, ни аллокаций.
- **Транспорт:** рукопожатие (в том числе потерянный `ConnectAccepted`), cookie, отказы по версии; надёжный канал при 20 % потерь
  и перестановке; надёжное сообщение больше `MaxReliableMessageBytes` отвергается кодером; keepalive и таймаут; смена адреса
  с проверкой пути; лимиты; повтор пакетов; клиентский `UdpDatagramSocket` на loopback — без исключений и аллокаций.
- **Снапшоты:**
  - дельта и полный кадр дают одно и то же; при потере подтверждений уходят ключевые кадры;
  - бюджет на полном бот-матче 3×3 и на 10 бойцов: в среднем ≤ 250 Б, максимум ≤ 1200 Б;
  - **свойство видимости:** на всех тиках полного бот-матча ни один снапшот команды k не содержит бойца или мину, невидимых
    для k, а событие по скрытой от k цели не несёт точки и слота цели и уходит только клиенту источника.
- **Сервер:** вводы применяются на своих тиках, работают повтор, перенос нажатия (фронт, один прицел на тик) и окно тиков;
  отсчёт отрицательными тиками; подмена ботом и возврат, AFK, итог. `ReplayVerifier`: повтор по журналу даёт тот же `ContentEquals`.
- **Клиент + сервер** в условиях CI (GDD §8.3: RTT 150 мс, 2 % потерь, 50 мс джиттера) и в «плохих» условиях (250 мс, 5 %,
  потери пачками). 2 и 6 бот-клиентов (`BotController` на стороне клиента видит только состояние показа — как человек), полный матч.
  Пороги в **условиях CI**:
  - ошибка предсказания своего бойца при сверке (без внешних толчков): p99 < 0,05 клетки, поправок больше 0,25 клетки — ноль;
  - «телепорты» — смещение вида за кадр больше «скорость × кадр × 3 + 0,3 клетки» без спавна, рывка или толчка — ноль;
  - недобор интерполяции (кадры экстраполяции) < 2 %, p99 длительности < 100 мс;
  - поздние и пропущенные вводы на сервере < 1 % тиков;
  - трафик в среднем ≤ 10 КБ/с вниз и ≤ 4 КБ/с вверх;
  - итог у всех клиентов совпадает с серверным, исключений нет, аллокаций в установившемся режиме нет (ни на сервере,
    ни на клиенте).
  В **«плохих» условиях** (серии потерь неизбежно дают поправки и догоняния): матч доходит до конца, итоги совпадают, исключений и
  аллокаций нет, p99 ошибки предсказания < 0,25 клетки, телепортов больше 1 клетки — ноль.
- **Переподключение:** обрыв на 10 с → бот через 1,5 с → возврат по токену → управление снова у игрока; случай «61 с»;
  перезапуск клиента с сохранённым токеном; смена адреса.
- **Лобби:** от 1 до 12 клиентов, добор ботами на 15-й секунде (виртуальные часы), разведение по командам, отмена,
  два матча параллельно, техработы.
- **Детерминизм и режим предсказания:** теневая симуляция совпадает с сервером для своего бойца на тех же вводах (без внешних
  эффектов); RNG не трогается; `FighterState` других бойцов бит в бит не меняется за N тиков предсказания; с `Predicting = false`
  всё ведёт себя как раньше (старые тесты зелёные).
- **Долгий тест:** 10 полных бот-матчей подряд по плохой сети — категория `Long`. **Нагрузка:** 100 матчей × 6 лёгких клиентов
  в одном процессе — время `MatchHost.Tick` на матч и байты (категория `Perf`). Обе категории в обычном прогоне `test.ps1` не
  запускаются: ключ `-Category` у `test.ps1` (Unity `-testCategory`, отрицание `!`) или `[Explicit]` — что сработает, записать
  в Decisions (S3.15).

### 12.2 MatchRunner: офлайн и онлайн без переписывания боя

- `IMatchDriver` (в Gameplay) — контракт «тик за тиком», ровно как офлайн-цикл сейчас: `Defs`, `Setup` (слоты), `State` — состояние
  показа последнего тика, `Events` — события этого тика, `LocalSlot`, `LocalTeam`, `IsEnded`; `int BeginFrame(float dt)` — сколько тиков
  выполнить в этом кадре (аккумулятор драйвера, не больше `MaxTicksPerFrame`); `void Step(LocalInputCollector input)` — один тик:
  ввод → тик → новые `State` и `Events`; `float Alpha` — доля тика для интерполяции видов. После каждого `Step` раннер делает то же,
  что сейчас после `RunTick` (`HitFeedback.Process`, `MapView.OnTileBroken`, `Capture` видов), поэтому `MatchViewState`,
  `ProjectileViewPool`, `AreaViewPool`, телеграфы и HUD по устройству не меняются — только читают `runner.Driver.State`.
  Отдельный «источник поз» не нужен.
- `OfflineMatchDriver` — нынешняя логика `MatchRunner` (симуляция, боты, аккумулятор, примагничивание), поведение не меняется.
  `MatchRunner.Simulation` и `MatchRunner.Bots` остаются (у офлайн-драйвера; в онлайне — `null`): PlayMode- и EditMode-тесты этапа 2
  не правятся и остаются зелёными.
- `OnlineMatchDriver` (Arena.Online) работает поверх `MatchClientSession`: `BeginFrame` — по часам предсказания (§2.3), `Step` —
  ввод → примагничивание → квантование → тень (§2.5) → отправка → **состояние показа** этого тика:
  - `State.Globals.Tick` = `Tpred + 1` после предсказания тика `Tpred` — как офлайн-состояние после своего тика (кадр снапшота тика T —
    состояние перед симуляцией T; уточнено в S3.7b, D-097); свой боец, его статусы, свои снаряды и зоны — из тени;
  - чужие бойцы, чужие снаряды (по сегментам) и зоны, подборы, клетки и режим — из интерполяции на `renderTick`, а их **тиковые
    поля** (появление, срабатывание, конец, доступность подбора, отсчёт, конец матча, `TeamRevealUntilTick`) сдвигаются на
    `Tpred − round(renderTick)`. Виды сравнивают их с `state.Globals.Tick` (телеграф, дуга навеса, таймер), и так чужое
    показывается в своём времени, а своё — сразу;
  - HP и макс. HP своего — из снапшота на `renderTick`: полоска и число урона по себе меняются вместе с долетевшим на экране снарядом;
  - слоты показа для снарядов и зон — своя таблица «ключ → слот» (свой снаряд: тик выпуска, способность, номер в залпе; чужой:
    слот сервера + `SpawnTick`), устойчивая между пересчётами тени: пулы видов узнают «тот же снаряд» по слоту и `SpawnTick`, как сейчас;
  - события — свои `AbilityFired` с переднего края тени и серверные по расписанию §2.6;
  - по `MatchEnded` драйвер пишет статистику слотов и итог режима в `State.Stats` и `State.Mode` — экран итогов и MVP работают
    без изменений.
- HUD и итоги (`ScoreBarView.Apply`, `ResultsScreen.Show`, `AbilityHudInfo.From`, `AcornsModeView`) принимают `(MatchDefs, MatchState)`
  вместо `MatchSimulation` — механическая замена, их тесты правятся на ту же сигнатуру. Счёт желудей HUD — из `ModeState` (S3.5),
  а не сумма по бойцам: скрытого носителя в состоянии показа нет.
- `MatchRunner` становится хостом видов. Драйвер он получает от `OnlineMatchBootstrap` — компонента сцены Match, который
  выполняется раньше раннера (как `MatchHud`, D-049), — а если его нет, создаёт офлайн-драйвер.
- `HitFeedback.Process(events, state)` не меняется.

### 12.3 Сессия между сценами

- `OnlineSession` (Arena.Online, `DontDestroyOnLoad`) создаётся в сцене Boot кодом `SceneBuilder`. Он держит `NetClient`
  (сокет, лобби, матч), опрашивает сеть первым каждый кадр (`DefaultExecutionOrder` раньше `MatchHud`: принятые снапшоты учтены до
  тиков кадра), обрабатывает `OnApplicationPause/Focus`, ведёт `RejoinStore` и выбор региона (DNS — в фоне, §3.2).
- `NetConfig` (SO, `Data/Net/NetConfig.asset`, сидер): регионы, ссылка на пакет данных `ArenaContent.bytes`, параметры «C» из §13.
- **Поток:** Menu → «Играть» → `MatchmakingScreen` → `MatchAssigned` / `MatchStart` → `SceneFlow` грузит Match с
  `MatchLaunchParams.Online` → `ClientReady` → отсчёт → бой → `MatchEnded` → итоги. «Ещё раз» снова ставит в очередь с тем же
  бойцом и режимом, «Меню» возвращает в меню.
- Android: `PlayerSettings.Android.forceInternetPermission = true` (в `ProjectConfigurator`). HTTP клиент не использует.
- Dev-инструменты только в Development-сборках, включаются из настроек: оверлей сети (RTT, джиттер, потери, запас ввода,
  задержка интерполяции, поправки) и симулятор задержки и потерь.

## 14. План реализации

Каждый шаг — одна сессия агента по рабочему циклу CLAUDE.md §3: в конце compile 0 CS, все тесты зелёные (сейчас 388 EditMode +

### S3.13 — Компенсация лага и защита

**Цель.** Ближний бой честен для атакующего при 150 мс (§2.8); атаки на протокол отбиваются.

**Сделать.**
- Core: `MatchState.PositionHistory` (позиция и «жив» на `MaxRewindTicks` тиков; в `CopyFrom`, `ContentEquals`, `Clear` и
  `StateEqualityTests`), `PlayerInput.ViewDelayTicks` (byte; в `Equals`, сохраняется в `Sanitized`), `LagCompensation.TargetPosition`;
  откат в `AbilitySystem.HitCone`, `HitSelfArea`, касаниях `DashSystem` и в автоприцеле этих доставок. Офлайн и боты дают
  `ViewDelayTicks = 0` — поведение не меняется.
- Сервер: ограничение задержки (§2.8), лимиты, счётчики подозрительного. Клиент: вычисление `ViewDelayTicks`.

**Тесты.** Удар лапой по цели, которую клиент видел при RTT 150 мс и джиттере 50 мс: с компенсацией — попадание, без неё — промах.
Предел 350 мс; завышенный `ViewDelayTicks` урезается; цель, возродившаяся в окне, — без отката. Снаряды — без отката. Атаки на
протокол (поддельный `connectionId`, повтор, флуд, вводы вне окна, мусор) отбрасываются, сервер продолжает работать.

**Готово, когда:** тесты выше зелёные; `ReplayVerifier` проходит матч с компенсацией (задержка — часть ввода в журнале).

### Риски

| Риск | Как снимаем |
| --- | --- |
| Ошибки своего транспорта | Детерминированные тесты на виртуальной сети с враждебными условиями, фаззинг, self-test по настоящему UDP. План Б — адаптер LiteNetLib (Q-013) |
| Ощущение предсказания при 150 мс («резинка», рывки) | Метрики поправок в тестах и на телефонах (оверлей, статистика клиента), сглаживание, параметры в конфиге, плейтесты |
| Расхождение float IL2CPP ARM64 и сервера | Одни Defs из пакета данных, прицел без тригонометрии, точное своё состояние в каждом снапшоте, пересчёт на каждом снапшоте и сглаживание. Мерить поправки на телефоне |
| Мобильные сети: запрет UDP, CGNAT, сети только с IPv6 | Понятная ошибка, keepalive, имя хоста и семейство сокета по DNS. Запасной путь через TCP или ретранслятор — после MVP |
| Всплески трафика (ульты, королевская битва) | Сегменты снарядов, приоритеты, AOI, тесты бюджета, `SnapshotRateDivisor` |
| Аллокации в сетевом коде под Mono/IL2CPP | Подключённый сокет без исключений, предвыделенные буферы, `AllocationAssert` |
| .NET SDK не установлен | Bootstrap-сборка (проверена зондом и рецензентом; с `rollForward: Major` запускается и на VPS с любым .NET ≥ 6) |
| Сервер на Windows (ICMP-сброс, грубый таймер, культура ru-RU) | `SIO_UDP_CONNRESET`, `timeBeginPeriod(1)`, InvariantCulture (§3.2, §5.2, §5.3) |

| Нет шифрования на этапе 3 | Ограниченный ущерб; ключи от HTTPS-бэкенда на этапе 4 (D-088) |
| Данные клиента и сервера разъехались | Один файл пакета данных для обоих, хэш в заголовке, тест-сторож экспорта |
| Ошибки потоков в хосте | Этап 3 — один игровой поток; многопоточность — только по итогам S3.15, логика однопоточная и под тестами |
