# Архитектурные решения

Формат: `D-NNN — решение. Причина.` Новые решения дописывать в конец (следующий свободный номер), с шагом и датой.
Числа, которых нет в GDD и которые выбрал агент, — с пометкой `PROTO` (раздел в конце).

## Базовые (план, 2026-10-18)

**D-001 — Своя симуляция боя вместо Photon Fusion 2 на этапе 2.** `Arena.Core` — детерминированная симуляция по тикам 30 Гц
с отдельной структурой ввода. GDD §12.2 требует Fusion в режиме Single, но SDK требует регистрации, а аккаунты создавать нельзя.
Причина: бой останется «под сеть» — на этапе 3 Fusion подключается обёрткой (D-038) без переписывания логики.
**Этап 3: Fusion не используется — своё серверное решение (D-063, `Docs/Server-Spec.md`).**

**D-002 — `Arena.Core` — чистый C# (`noEngineReferences: true`), состояние — blittable struct в предвыделенных массивах.**
`MatchState` содержит `MatchGlobals` и массивы `FighterState[]`, `ProjectileState[]`, `AreaState[]`, `StatusEffectState[]`,
`PickupState[]`, тайлы карты, `ModeState`. Никаких ссылочных полей, строк и списков в состоянии. Снапшот — `CopyFrom` (Array.Copy).
Причина: логика тестируется без движка, запускается на headless-сервере, состояние легко снимать/восстанавливать и маппить
на `NetworkArray<T>` Fusion; нет аллокаций в тике.

**D-003 — Время в состоянии — тики (`int`), здоровье и урон — `int`.** Конфиги хранят секунды/проценты; конвертер переводит
в тики (`SimTime.SecondsToTicks`, округление к ближайшему). Причина: точные сравнения, совместимость с `TickTimer` Fusion,
нет накопления ошибок float в таймерах.

**D-004 — Ёмкости массивов — константы `SimLimits`** (`MaxFighters = 10` под королевскую битву, `MaxProjectiles = 256`,
`MaxAreas = 64`, `MaxStatusEffects = 128`, `MaxPickups = 64`, `MaxEvents = 256`, `TickRate = 30`). Это технические пределы,
а не игровые параметры — исключение из правила «нет магических чисел». Причина: `[Capacity(N)]` у Fusion должна быть константой
компиляции; переполнение обрабатывается без исключений (счётчик отброшенного).

**D-005 — Математика: свой `Vec2` на `float` и `System.MathF`; RNG — свой struct (xorshift128+/PCG32), seed и состояние — в
`MatchGlobals`.** Требуется детерминизм в пределах одной сборки/платформы (проверяется тестами), побитовый детерминизм между
платформами не нужен: сервер на этапе 3 авторитарный. Причина: проще и быстрее fixed-point, достаточно для авторитарной модели.

**D-006 — Ввод: `struct PlayerInput { Vec2 Move; Vec2 Aim; InputButtons Buttons; }`** — аналог `INetworkInput`.
`Move` и `Aim` — длина ≤ 1; `Aim` — направление × доля дальности (для навесных атак). `InputButtons` (`[Flags] byte`):
`Attack`, `Ult`, `Trick`, `AutoAim`. Кнопки «выстрел» одноразовые: локальный сборщик защёлкивает нажатие до ближайшего тика
и выдаёт его ровно в одном `PlayerInput`; симуляция дополнительно хранит `PrevButtons` в `FighterState` и реагирует на фронт.
Причина: стик «потяни-отпусти» даёт событие между тиками — его нельзя потерять; фронт защищает от повторов при ресимуляции.

**D-007 — Автоприцел считается в симуляции**, а не на клиенте: флаг `AutoAim` → `TargetingSystem` выбирает ближайшего видимого
команде стрелка врага в радиусе атаки, иначе — по направлению взгляда. Причина: серверная проверка (GDD §8.1), одинаковое
поведение у игрока и бота.

**D-008 — События тика (`SimEventBuffer`: попадание, смерть, возрождение, выстрел, подбор, поломка стены, ульта готова) —
вне снапшота**, очищаются в начале каждого тика; виды читают их после тика. Причина: обратная связь (числа урона, вспышки)
без опроса всего состояния; на этапе 3 события восстанавливаются клиентом из состояния/RPC.

**D-009 — Координаты.** Core `Vec2(x, y)` ↔ Unity `(x, 0, y)`; 1 клетка = 1 юнит; клетка `(c, r)` имеет центр `(c+0.5, r+0.5)`;
начало карты — `(0, 0)`, команда 0 внизу (малые `y`), команда 1 вверху. Причина: однозначное соответствие сетки и мира.

**D-010 — Данные: ScriptableObject-конфиги → чистые Core-Defs.** Классы SO — `Assets/_Project/Scripts/Data` (asmdef `Arena.Data`,
ссылается на Core и Bots), ассеты — `Assets/_Project/Data/{Fighters,Maps,Modes,Combat,Bots,Feel,Localization,Economy}`.
Корневой SO `GameDatabase` ссылается на всё; сцены ссылаются на него (без Resources/Addressables на этапе 2). Ассеты создаёт
`Arena.Editor.Data.DataSeeder.SeedAll`; **на этапе 2 сидер — источник правды и перезаписывает значения** (идемпотентно).
Причина: агенты не открывают редактор; после начала ручного тюнинга сидер переключим на «создавать только отсутствующие» (Q-005).

**D-011 — Способности = доставка + эффекты + условные модификаторы.** `AbilityDef { DeliveryKind; параметры доставки;
EffectDef[] }`, `EffectDef { EffectKind; TargetFilter (Enemy/Ally/Self); Value; Duration; Distance }`,
`TalentDef { TalentCondition; TalentModifier; Value; Param }`. Атака, ульта и трюк используют один `AbilitySystem`.
Эффекты — маленькие статические обработчики (`DamageEffect`, `KnockbackEffect`, `StunEffect`, `HealEffect`, `DashEffect`,
`ShieldEffect`/`DamageReduction`, `InvisibilityEffect`, `MarkEffect`, …). Новый боец — новые данные. Причина: GDD §4, §12.2.

**D-012 — Уровни в прототипе.** `MatchSetup` хранит уровень бойца (по умолчанию 1) и флаг `UnlockAllAbilities = true`:
трюк и талант доступны сразу, хотя по GDD открываются на 5 и 8 уровнях. Причина: тестерам нужно попробовать весь бой;
прокачки нет до этапа 4. Вопрос — Q-003.

**D-013 — Числа, которых нет в GDD** (скорости снарядов, радиусы бойцов, интервалы очередей, порог заряда ульты, сила «лёгкого
отброса», радиус обзора бота, задержки), агент выбирает сам, кладёт **только в сидер** и записывает в раздел PROTO ниже.

**D-014 — Виды: префабы и материалы создаются кодом (`ViewAssetBuilder`), рантайм — пулы.** Префабы в `Assets/_Project/Art/Prefabs`,
материалы (URP Lit/Unlit) — в `Assets/_Project/Art/Materials`, ссылки — через SO `ViewCatalog`. В рантайме нет `Shader.Find` и
`GameObject.CreatePrimitive`. Смена цвета (вспышка, полупрозрачность в кусте, свой/чужой) — подменой общего материала,
не `MaterialPropertyBlock`. Причина: шейдеры не вырежутся из сборки, SRP Batcher работает, арт заменяется правкой префаба.

**D-015 — Отображение интерполирует между двумя последними тиками; предсказания офлайн нет; стоп-кадр ульты — только визуальный.**
Причина: офлайн задержка ≤ 1 тика (33 мс); на этапе 3 добавится предсказание своего бойца (GDD §8.1). Стоп-кадр в симуляции
невозможен на сервере, поэтому замораживаются только виды на 40 мс.

**D-016 — Камера:** фиксированный угол ~55° (из `CameraConfig`), по горизонтали — центр карты, по длинной оси следует за игроком
с ограничением краями карты. Для команды 1 камера повёрнута на 180° вокруг центра карты, и ввод поворачивается так же
(в `LocalInputCollector`), — «своя база внизу». Причина: GDD §5.5; карта 21×31 целиком на экран телефона не влезает.

**D-017 — Ввод: только Input System (`activeInputHandler = 1`).** Сенсорные стики — uGUI (`IPointer*Handler` через
`InputSystemUIInputModule`), ПК/редактор — прямой опрос `Keyboard.current`/`Mouse.current` (без `InputActionAsset`).
Всё сводится в `LocalInputCollector` → `PlayerInput`. Причина: один путь для мыши и касаний, без аллокаций, без GUI-настройки.

**D-018 — UI строится в рантайме кодом** по SO `UiStyle` (размеры, отступы, цвета, встроенные спрайты `UI/Skin/*`).
Шрифт этапа 2 — встроенный `LegacyRuntime.ttf` (uGUI `Text`, динамический, кириллица через системный фолбэк).
TextMeshPro + Rubik/Nunito (OFL) — на этапе 5. Причина: импорт TMP Essentials в batchmode — лишний риск ночью; без внешних шрифтов.

**D-019 — Локализация этапа 2 — своя таблица** `LocTable` (SO: ключ, en, ru) + `Loc.Get(key)`; ключи — константы `Loc.Keys`.
Переход на Unity Localization — этап 4–5. Причина: Unity Localization тянет Addressables и отдельный шаг сборки контента;
в прототипе мало строк. Вопрос — Q-004.

**D-020 — Активная платформа проекта всегда Android** (`-buildTarget Android` во всех запусках). Сборка: IL2CPP, ARM64,
minSdk 26 (Android 8.0), Vulkan + GLES3, ASTC, только landscape, APK (не AAB) в `Builds/Android/`.
Причина: нет переимпорта при переключении платформ; параметры — GDD §8.4.

**D-021 — Проект создаётся `-createProject` без шаблона URP**, URP и прочее — пакетами и кодом. Причина: шаблон приносит
примеры, лишние пакеты и ассеты; чистый проект детерминированно настраивается `ProjectConfigurator`.

**D-022 — Боты — отдельный чистый asmdef `Arena.Bots`** (ссылается на Core), с собственным RNG в состоянии бота, решения
раз в 0,2 с. Бот видит только врагов, видимых его команде (кусты, невидимость), и в радиусе обзора (`PROTO`, ≈ размер экрана) —
аналог «не знает позиций за пределами экрана». Причина: GDD §7; боты пойдут на сервер этапа 3 без изменений.

**D-023 — Пакеты ставятся `UnityEditor.PackageManager.Client.AddAndRemove`** из Editor-скрипта без указания версий
(Package Manager выбирает рекомендованные для редактора); запасной путь — версии в `manifest.json`. Состав: URP, Input System,
Test Framework, uGUI; убираются collab-proxy, visualscripting, multiplayer.center, timeline. Причина: агент не угадывает версии.

**D-024 — Видимость.** Боец виден чужой команде, если выполняется хотя бы одно: не в кусте и не невидим; враг этой команды
ближе `BushRevealDistance` (2 клетки; к невидимому — не действует); боец атаковал за последние 1 с (раскрытие, снимает и
невидимость); помечен этой командой (метка Новы); у команды активно раскрытие (ульта Новы). Союзники видят друг друга всегда.
Своего бойца в кусте рисуем полупрозрачным. Невидимость (трюк Векса) скрывает на любом расстоянии, пока не атакует.
Причина: GDD §5.2 + однозначные правила для тестов и ботов.

**D-025 — «Жёлуди», уточнения.** Золотой жёлудь — дополнительно к обычному на 60 и 120 с. При поражении бойца его жёлуди
рассыпаются как обычные (золотой = 3 обычных), подобрать можно через `PickupDelay` (`PROTO` 0,5 с). Отсчёт идёт для команды
с бо́льшим числом желудей, если у неё 12+; при равенстве 12+ отсчёт сбрасывается. Подбор — касанием (радиус бойца + радиус
жёлудя). Причина: GDD §5.4 не описывает эти случаи.

**D-026 — Бойцы не сталкиваются друг с другом**, только со стенами и водой. Причина: стандарт жанра, меньше застреваний и
рассинхрона на этапе 3.

**D-027 — Без динамических теней:** под бойцами — тени-кружки (квад с прозрачной текстурой, сгенерированной кодом). Причина: GDD §8.4.

**D-028 — Звуки этапа 2 — процедурные** (`AudioClip.Create` из синусов/шума при старте, параметры в `FeelConfig`). Причина:
нет ассетов и лицензий; оригинальный контент.

**D-029 — Палитра команд:** свои — синий, враги — красный, с заметной разницей яркости; в настройках — палитра для дальтоников
(синий/оранжевый). Цвета — в `UiStyle`/материалах. Причина: GDD §5.3.

**D-030 — Мина Чомпа** видна своей команде всегда, врагам — по правилам видимости кустов (ближе 2 клеток). Причина: в GDD не задано;
иначе мина бесполезна.

**D-031 — Возрастной гейт — на этапе 4** (вместе с аккаунтом). Прототип этапа 2 не собирает данных, не имеет чата, рекламы, ссылок и
покупок — соответствует «ограниченному режиму». Вопрос — Q-001.

**D-032 — Сцены `Boot`, `Menu`, `Match` целиком генерирует `SceneBuilder.BuildAll`** и содержат только бутстрап-объекты (камера, свет,
EventSystem, раннер со ссылками на SO). Карта, бойцы, HUD создаются в рантайме из данных. Причина: YAML не пишем руками, сцены
пересоздаются без конфликтов.

**D-033 — Инструменты и проверки.** `Tools/*.ps1` совместимы с PowerShell 5.1, всё пишут в `Tools/out/`, итог — одной строкой, коды
0/1/2/3. Отсутствие аллокаций проверяется тестом через `GC.GetAllocatedBytesForCurrentThread()` после прогрева; детерминизм — двумя
симуляциями и снапшотом. Причина: агенты работают только через batchmode, итог должен читаться машинно.

**D-034 — Идентификатор пакета `com.arena.prototype`, отладочный keystore.** Причина: юрлицо и название не выбраны (GDD §13);
для теста на телефоне подписи отладки достаточно. Вопрос — Q-002.

**D-035 — На этапе 2 нет папки `Net` и режима «Тренировка».** Тренировка = матч с ботами «Новичок» (выбор в меню). Причина: этап 2
по GDD §3 — только «Жёлуди»; пустые папки дают в git «висящие» `.meta`.

**D-036 — Движение мгновенное, без инерции:** скорость сразу равна `move × speed`. Причина: отзывчивость, проще предсказание на этапе 3.

**D-037 — Частота кадров:** `Application.targetFrameRate = 60`, `vSyncCount = 0`, настройка «экономия» — 30. Причина: GDD §8.4.

**D-038 — План подключения Fusion (этап 3).** Один `NetworkObject` «Match» с `NetworkBehaviour`, который в `FixedUpdateNetwork`
собирает `PlayerInput` всех игроков (`GetInput`), вызывает тот же `MatchSimulation.Tick`, а массивы состояния лежат в
`[Networked, Capacity(SimLimits.X)] NetworkArray<FighterState>` и т. п. (struct станут `INetworkStruct`). `MatchRunner` этапа 2 — это
локальная реализация того же цикла. Причина: фиксирует ограничения для Core уже сейчас (blittable, константные ёмкости, тики).
**Заменено D-063 (2026-10-18): Photon Fusion не используется; ограничения для Core остаются в силе — они нужны снапшотам и пересчёту.**

**D-039 — Журнал ночи:** после рабочего коммита шага строка в `Docs/NightLog.md` с его хешем — отдельным коммитом `docs: night log Sx.y`.
Причина: хеш известен только после коммита; история не переписывается.

## Этап 3 «Онлайн» — своё серверное решение (ТЗ `Docs/Server-Spec.md`, 2026-10-18)

- D-063 (S3 ТЗ, 16:40) — **Своё серверное решение вместо Photon Fusion (решение пользователя).** Авторитарный выделенный
  сервер — наш процесс .NET; без Photon, Edgegap и любых платных сервисов. Заменяет D-038. Ограничения ядра из D-002/D-004/D-038
  (blittable-состояние, константные ёмкости, тики) остаются — они нужны снапшотам и пересчёту. Q-006 закрыт. Тексты GDD §4,
  §8.1–8.2, §13 про Photon и Edgegap устарели; правка — с разрешения человека (Q-017). Причина: решение пользователя;
  бесплатно и под нашим управлением.
- D-064 (S3 ТЗ) — **Модель сети: авторитарный сервер + интерполяция снапшотов для чужих + предсказание и сверка своего бойца той
  же `MatchSimulation`** (ТЗ §2). Lockstep и одноранговый rollback отвергнуты. Зонд показал: тот же код с тем же сидом на CoreCLR x64
  и на Mono x86 из Unity расходится с тика 83 (6 ботов), исход матча другой — побитового детерминизма между рантаймами нет,
  а клиент на IL2CPP ARM64 — третья комбинация. Кроме того, обе схемы раскрывают клиенту скрытое (кусты). Причина: GDD §4, §8.1;
  честность, устойчивость к недетерминизму, 10 игроков.
- D-065 (S3 ТЗ) — **Транспорт — свой UDP на `System.Net.Sockets` (`Arena.Net.Transport`).** Пакет ≤ 1200 байт, заголовок 18 байт,
  подтверждения ack + 32 бита. Ненадёжный канал — для ввода и снапшотов, надёжный упорядоченный — для управления; фрагментируются
  только надёжные сообщения. Клиент — подключённый сокет (без аллокаций `EndPoint` под Mono/IL2CPP), сервер — API `SocketAddress`
  .NET 8+. LiteNetLib (MIT) — запасной вариант через адаптер (Q-013; это противоречит D-040 «готовое вместо своего» — решает человек).
  Unity Transport, NGO/NfE, Mirror, FishNet отвергнуты: сервер стал бы процессом Unity. Причина: один код в Unity и .NET, контроль
  аллокаций и безопасности, нужен малый набор функций, скачивание вне реестра Unity запрещено.
  **Уточнено рецензией (D-082):** фрагментации нет — каждое надёжное сообщение ≤ 1000 Б.
- D-066 (S3 ТЗ) — **Сервер — консольный процесс .NET 10 (LTS), много матчей в одном процессе.** Матч закреплён за рабочим потоком,
  приём идёт в отдельном потоке через SPSC-кольца, лобби и матчи — на одном UDP-порту. Исходники Core/Bots/Net общие с Unity
  (ссылки из `Server/*.csproj`, без копий). Unity Dedicated Server отвергнут: модулей нет, процесс тяжелее, Mono медленнее
  (0,015 против 0,004 мс/тик в зонде). Пока .NET SDK не установлен — bootstrap-сборка встроенным в Unity Roslyn против .NET 6.0.21:
  Core+Bots (96 файлов) собрались без правок за 0,8 с. Bootstrap — только для разработки. Причина: ядро уже без UnityEngine,
  CoreCLR быстрее, есть Docker и ARM64.
  **Уточнено рецензией (D-084):** на этапе 3 — один игровой поток; bootstrap-сборка пригодна и для VPS.
- D-067 (S3 ТЗ) — **Раскладка кода.**
  - `Arena.Net` — чистый C#, ссылается на Core и Bots, общий с сервером.
  - `Arena.Net.Server` — чистый C#; в Unity только Editor (для тестов), в APK не попадает.
  - `Arena.Online` — Unity-слой.
  - `Server/Arena.Shared` — netstandard2.1, ловит API, которых нет в Unity.
  - `Server/Arena.Server` — net10.0, хост.

  Общие файлы — на C# 9 и .NET Standard 2.1, без records/`init`, covariant returns, module initializers и `SkipLocalsInit`.
  В `.gitignore` нужно `!Server/**/*.csproj`: сейчас `*.csproj` игнорируется. Тесты — Unity EditMode + консольный `--selftest`,
  NuGet не нужен. Причина: одна логика и в тестах, и на сервере; без скачиваний.
- D-068 (S3 ТЗ) — **Данные сервера — канонический двоичный пакет `Server/content/arena-content.bin`.** Экспортирует Editor-метод
  `ContentPackExporter` из тех же Defs, что строит `ConfigConverter`. `ContentHash` — 8 байт SHA-256; версия формата —
  `NetProtocol.Version`; несовпадение → экран «Обновите игру». Тест-сторож: экспорт из текущих ассетов совпадает с закоммиченным
  файлом. Причина: сервер не читает ScriptableObject; GDD §8.3.
  **Уточнено рецензией (D-083):** один файл `Assets/_Project/Data/Net/ArenaContent.bytes`, онлайн-клиент берёт Defs из него, хэш — в заголовке.
- D-069 (S3 ТЗ) — **Снапшоты собираются для каждого клиента отдельно.**
  - Фильтр на сервере до кодирования: видимость команды (`VisibleToTeams`, мины по D-030) и AOI.
  - Дельта к новейшему подтверждённому (кольцо на 32), иначе ключевой кадр.
  - Свой боец — все поля `FighterState` точно, остальное квантовано.
  - Снаряды — сегментами (начало, направление, тик), клетки — изменениями, события — с последнего подтверждённого снапшота,
    с тем же фильтром, что в `HitFeedback`.
  - Размер ≤ 1200 байт, с приоритетами.

  Оценка: ≈ 4–5 КБ/с вниз, ≈ 2 КБ/с вверх. Причина: GDD §8.1 (10 КБ/с), античит «сквозь кусты», устойчивость к потерям.
  **Уточнено рецензией (D-082):** события — подмножество с избыточностью 3 тика; при скрытой цели — только источнику, без точки.
- D-070 (S3 ТЗ) — **Время и ввод.**
  - Клиент опережает сервер на запас ввода. Сервер в каждом снапшоте сообщает `InputMarginTicks`, клиент подстраивает темп тиков
    (±5 %; при ошибке > 10 тиков — прыжок).
  - Ввод квантуется до предсказания и до отправки, в пакете — 4 последних ввода.
  - На сервере: окно тиков; если ввода нет — повтор последнего движения без кнопок до 200 мс; нажатие из опоздавшего ввода
    переносится на ближайший тик.
  - Чужие интерполируются с адаптивной задержкой ≈ 100 мс, экстраполяция — не дольше 120 мс. События выдаются по времени показа,
    свои — сразу.

  Причина: GDD §8.1; D-006 (нажатия не теряются).
  **Уточнено рецензией (D-079, D-082):** отсчёт — отрицательные тики; запас ввода — минимум за окно; прицел — 2 × int16.
- D-071 (S3 ТЗ) — **Режим предсказания в Core: `MatchGlobals.PredictionSlot`** (−1 — сервер и офлайн).
  - Предсказываются: движение, рывки, идущий отброс, заряды, очередь, траты ульты и трюка, возрождение, свои снаряды и зоны (для видов).
  - Эффекты — только свои на себя.
  - Не предсказываются: урон, лечение, эффекты на других и от других, заряд ульты от урона, крюк Векса, правила режима, RNG, реген.
  - Видимость чужих берётся из снапшота.

  Пересчёт — только если своё состояние не совпало. Поправка затухает за 0,1 с, больше 3 клеток — применяется сразу.
  Причина: GDD §5.3 (отклик ≤ 1 кадра); без ложных попаданий и мерцания HUD.
  **Заменено рецензией (D-080):** `Predicting` (bool) + `PredictedSlot`, правило «действует только свой боец», пересчёт на каждом снапшоте.
- D-072 (S3 ТЗ) — **Компенсация лага — только для мгновенных контактных попаданий** (`MeleeCone`, `SelfArea`, касания `Dash`).
  Позиции целей берутся из `MatchState.PositionHistory` на `ViewDelayTicks` назад, с пределом 250 мс и оценкой сервера.
  Снаряды, навес и мины — без отката. Причина: GDD §8.1 требует учитывать пинг стрелявшего. Но уворот от снаряда — основной
  навык цели, автоприцел и так решается на сервере, навес телеграфируется, а откат снарядов давал бы «попадания за стеной».
  **Уточнено рецензией (D-085):** предел 350 мс, история 12 тиков, автоприцел отката по тем же позициям.
- D-073 (S3 ТЗ) — **Лобби и матчмейкинг — в том же процессе и на том же UDP-порту** (надёжные сообщения), не HTTP.
  - Очередь по режиму, добор ботами через 15 с; люди и боты делятся поровну по командам; одинаковых бойцов разводим по командам.
  - Регион выбирается по `Ping`, LAN-сервер находится через `Discover`; адреса серверов — в `NetConfig` (ввода текста нет).
  - Анонимность: `InstallId` — случайные 128 бит в PlayerPrefs; серверу уходит только хэш `installKey`, он хранится в памяти
    и не пишется в логи. Имён и чата нет, IP не логируются.

  Причина: один порт и протокол, всё проверяется в EditMode, приватность GDD §2.
  **Уточнено рецензией (D-086):** `InstallId`/`installKey` убраны — постоянного идентификатора нет.
- D-074 (S3 ТЗ) — **Безопасность этапа 3.** Есть:
  - cookie-рукопожатие без состояния (SipHash);
  - запросы дополнены до 1200 байт — усиления нет;
  - случайный 64-битный `connectionId`, окно повторов;
  - проверка пути при смене адреса, лимиты.

  Шифрования и подписи пакетов секретным ключом нет: ключи выдаст HTTPS-бэкенд на этапе 4, флаг в заголовке зарезервирован.
  Причина: нет аккаунтов и личных данных, от читов шифрование не защищает, а свой криптокод сейчас — лишний риск (Q-016).
- D-075 (S3 ТЗ) — **Вылет и возврат.**
  - Без ввода 1,5 с — бойцом управляет бот; без пакетов 5 с — соединение потеряно.
  - Клиент переподключается 60 с (GDD §8.3) по `rejoinToken`; вернуться можно до конца матча.
  - После перезапуска приложения — кнопка «Вернуться в бой» (данные в PlayerPrefs).
  - AFK 20 с — бот; любое действие возвращает управление.
  - В «Последнем звере» выбывший слот не подменяется.

  `BotController` получает включение и выключение бота на слоте. Причина: GDD §7, §8.3; команда не страдает от вылета ребёнка.
  **Уточнено рецензией (D-087):** AFK — 30 с; в снапшоте флаг «бойцом управляет бот»; выбывшему — `Eliminated`.
- D-076 (S3 ТЗ) — **«Последний зверь» в симуляции.**
  - `ModeKind.LastBeast`, правила `LastBeastRules` на шаге 8a; команда = слот.
  - Ящики — `BoxState` поверх тайла `BerryBox`; их бьют снаряды, конусы и взрывы.
  - Ягоды — подборы `PickupKind.Berry`: +8 % урона и макс. HP, аддитивно.
  - Туман — сжимающийся квадрат с импульсами урона от среды.
  - Места — по порядку выбывания (выбывшие одновременно делят место), без возрождения (`RespawnEnabled`).

  Числа вне GDD — PROTO (Q-018). Делается до снапшотов (S3.3). Причина: GDD §5.4; сеть проектируется под худший случай — 10 бойцов.
  **Уточнено рецензией (D-080):** вместо `RespawnEnabled` — `NoRespawn` (значение по умолчанию сохраняет нынешнее поведение).
- D-077 (S3 ТЗ) — **Проверки этапа 3 без людей.**
  - EditMode на виртуальных часах и `InMemoryNetwork`: сервер и клиенты в одном процессе, детерминированно.
  - Условия CI GDD §8.3 (150 мс, 2 %, 50 мс) и «плохие».
  - Пороги: ошибка предсказания p99 < 0,05 клетки, поправок > 0,25 клетки — ноль, «телепортов» — ноль, недобор интерполяции < 2 %,
    поздних вводов < 1 %, трафик ≤ 10/4 КБ/с, итоги совпадают, 0 аллокаций.
  - Свойство видимости на полных бот-матчах, `ReplayVerifier`.
  - `--selftest` по настоящему UDP; нагрузка — 100 матчей на ПК.

  Причина: GDD §8, §3; агенты не играют на телефонах.
  **Уточнено рецензией:** строгие пороги — только в условиях CI; в «плохих» — мягкие (ТЗ §11.1).
- D-078 (S3 ТЗ) — **Развёртывание.**
  - Сначала ПК в LAN (правило брандмауэра добавляет человек).
  - Затем бесплатный VPS: кандидат — Oracle Always Free (ARM64), аккаунт создаёт человек (Q-014).
  - Docker — по желанию (`mcr.microsoft.com/dotnet/runtime:10.0`), есть systemd-сервис.
  - Метрики слушают только 127.0.0.1.

  Причина: бесплатно и под нашим управлением; агент не создаёт аккаунты и не меняет системные настройки.
  **Уточнено рецензией (D-084):** без SDK на VPS годится bootstrap-сборка (`rollForward: Major`, любой .NET ≥ 6).

## Этап 3 — рецензия ТЗ (2026-10-18, независимый агент; раздел «Рецензия» в `Docs/Server-Spec.md`)

- D-079 (S3 рецензия) — **Время матча: отсчёт — отрицательные тики.** У матча счётчик `T`; в фазе `Countdown` он идёт от
  `−CountdownTicks` до −1 без `MatchSimulation.Tick`, бой — с `T = 0` (тик симуляции = `T`). Снапшоты и ввод идут уже в отсчёте, тики
  в протоколе — zigzag-varint, `MatchStart` не несёт «тика старта». Запас ввода: сервер сообщает `InputMarginMin` — минимум
  `новейший тик пакета − T` за 30 тиков, клиент держит его на 1 тике темпом ±5 % (прыжок при ошибке ≥ 10). Причина: тик старта
  неизвестен до `ClientReady`; минимум прямо задаёт долю опоздавших вводов; к началу боя часы уже сошлись.
- D-080 (S3 рецензия) — **Режим предсказания и правило значений по умолчанию.** `MatchGlobals.Predicting` (bool, по умолчанию
  false) + `PredictedSlot`. В режиме действует только свой боец; эффекты — только свои на себя и не урон и не лечение; крюк и мины не
  срабатывают; реген, правила режима и RNG стоят; видимость считается только для своего. Тень пересобирается на каждом новом
  снапшоте: свой — точно, чужие — в показанных позициях, скрытые — `Active = false`, чужих снарядов в тени нет. Общее правило для всех
  новых полей Defs и состояния: 0 / false = нынешнее поведение (поэтому `NoRespawn`, а не `RespawnEnabled`). Причина: `Clear()`
  обнуляет `int PredictionSlot = −1` в слот 0, а `RespawnEnabled = false` выключил бы возрождение в тестах с ручными Defs — оба ломали
  бы старые тесты; пропуск пересчёта «если совпало» оставлял бы чужих в тени на старых местах.
- D-081 (S3 рецензия) — **Показ онлайн: `IMatchDriver` «тик за тиком» и одна временная линия в состоянии показа.** Драйвер даёт
  `BeginFrame(dt)` / `Step(input)` / `Alpha`; раннер после каждого шага делает то же, что сейчас (`Capture`, `HitFeedback`, `MapView`), —
  виды и пулы не перестраиваются. В состоянии показа `Tick` = тик предсказания, тиковые поля мира из снапшотов сдвигаются на
  `Tpred − renderTick`; HP своего — на `renderTick`; слоты показа — по ключу; итог — из `MatchEnded` в `State.Stats`. HUD и итоги
  принимают `(MatchDefs, MatchState)`, счёт желудей — из `ModeState` (`Team0Acorns` / `Team1Acorns`). `MatchRunner.Simulation` и `Bots`
  остаются для офлайна. Причина: виды сравнивают тиковые поля с `state.Globals.Tick`; скрытый носитель не попадает в снапшот;
  PlayMode-тесты читают `runner.Simulation`.
- D-082 (S3 рецензия) — **Протокол, уточнения.** Прицел — 2 × int16 (без тригонометрии: одинаковые биты на IL2CPP ARM64 и CoreCLR).
  Ключевой кадр — флагом. Сегмент снаряда несёт `SpawnTick`, маску задетых, пробития и отскоки, флаг отскока; конец снаряда — с
  точкой. События — только `Damaged`, `Healed`, `AbilityFired` ульты и `UltReady` своего, каждое в 3 снапшотах подряд; при скрытой от
  команды цели событие получает только клиент источника, без точки и слота цели. Флаг «своим бойцом управляет бот», сообщение
  `Eliminated`. Фрагментации нет (надёжное сообщение ≤ 1000 Б). Вид в кольце сервера = то, что восстановит клиент. Причина:
  идентичность снарядов при отскоке; тик 0 — настоящий; утечка точки врага в кусте через попадание союзника; объём «повтора до
  подтверждения» рос с RTT.
- D-083 (S3 рецензия) — **Пакет данных — один файл для клиента и сервера.** `ContentPackExporter` пишет
  `Assets/_Project/Data/Net/ArenaContent.bytes` (TextAsset, хэш в заголовке); `DataSeeder.SeedAll` вызывает экспорт сам; сервер
  получает копию при сборке; онлайн-клиент строит Defs из этого файла (`ContentBundle.CreateMatchDefs`), офлайн — из SO, как раньше.
  Причина: `ConfigConverter` на телефоне (float IL2CPP) мог бы дать другие биты Defs — вечный `ContentMismatch` и поправки
  предсказания; один файл — одна правда, SHA-256 на телефоне не нужен.
- D-084 (S3 рецензия) — **Сервер этапа 3: один игровой поток, Windows и bootstrap.** Приём (неблокирующий), тики и отправка — в одном
  потоке; поток метрик читает снимок счётчиков. Рабочие потоки — только если нагрузка S3.15 покажет нужду. На Windows
  `SIO_UDP_CONNRESET` выключен, `ConnectionReset` и `MessageSize` не роняют приём, `timeBeginPeriod(1)`. InvariantCulture везде.
  Bootstrap-команда проверена рецензентом (ТЗ §5.2: исключить нативные dll, `-preferreduilang:en-US`, runtimeconfig с
  `rollForward: Major` → запуск на любом .NET ≥ 6, в том числе на VPS). Запасной `PortableUdpServerSocket` (netstandard2.1) — в
  `Arena.Net.Server`. Причина: многопоточность — лишний риск при 1–10 матчах; без этих мер Windows-сервер падает или дрожит.
- D-085 (S3 рецензия) — **Компенсация лага, уточнения.** Предел 350 мс, `SimLimits.MaxRewindTicks` = 12 (история позиции и «жив»).
  Для мгновенных доставок по позициям отката считаются и автоприцел, и проверка попадания; эффекты, события, отброс и рассыпание
  желудей — по текущим; цель, не жившая весь интервал отката, — без отката. `ViewDelayTicks` — часть `PlayerInput` (попадает в
  журнал ввода). Причина: GDD §8.3 — RTT 150 мс и джиттер 50 мс дают до ≈ 350 мс задержки вида, предел 250 мс её не покрывал.
- D-086 (S3 рецензия) — **Приватность: постоянного идентификатора нет.** `InstallId` / `installKey` убраны: билет — на соединение,
  возврат после перезапуска — по `rejoinToken` из `RejoinStore`. Статистика клиента — только сетевая (без FPS). LAN-обнаружение
  выключено на VPS и отвечает только частным адресам. Причина: GDD §2 — минимум данных; идентификатор не был нужен ни для очереди,
  ни для возврата.
- D-087 (S3 рецензия, закрывает Q-015) — **Продуктовые правила онлайна по умолчанию.** Ботов не помечаем (GDD §13 — открытый вопрос,
  поле `isBot` в протоколе есть); одинаковых бойцов разводим по разным командам, если не вышло — разрешено; вернуться можно до конца

  а кубков пока нет). Человек может пересмотреть. Причина: решения не блокируют этап и меняются в конфиге.
- D-088 (S3 рецензия, закрывает Q-016) — **Уровень защиты этапа 3 — как в D-074.** Шифрования и подписи пакетов нет до HTTPS-бэкенда
  этапа 4. Причина: нет аккаунтов и личных данных, худший ущерб — перехват бойца в одном матче; свой криптокод сейчас — лишний риск.
  Человек может пересмотреть.
- D-089 (S3 рецензия, закрывает Q-018) — **Числа «Последнего зверя» — PROTO** (ТЗ §9, §13): прочность ящика 3600, из ящика 1 ягода,
  рост урона тумана +250/с за шаг, импульс 0,5 с, минимальная зона 5×5, предел матча 6 мин, ягоды аддитивно (×(1 + 0,08 × N)).
  S3.3 пишет их в таблицу PROTO; проверить после игры (как Q-008).
- D-090 (S3.1) — **Сетевой фундамент: кодер без исключений, единичные векторы с запасом, bootstrap-сборка.** (1) `BitWriter`/`BitReader`
  (LSB first, little-endian) при выходе за буфер не бросают исключение, а ставят `IsOverflow` и дальше пишут/читают нули — вызывающий
  проверяет флаг один раз и отбрасывает пакет (исключения выделяют память, а вход сети недоверенный). Битая varint (> 5 байт или
  биты за пределами 32) — тоже `IsOverflow`. (2) `Quantize.ToAim/ToMove` гарантируют x² + y² ≤ scale² − ⌈scale² / 100000⌉ (целая
  проверка; при необходимости большая по модулю компонента уменьшается на 1), кроме осевого полного отклонения (±scale, 0) —
  оно точно даёт длину 1. Так `PlayerInput.Sanitized()` на сервере никогда не пересчитывает квантованный ввод (FMA/округление
  на разных платформах не меняют ветку), и предсказание с сервером получают одни биты. Цена — длина ≥ 0,99997 по диагонали.
  Обратное преобразование — только деление. (3) Bootstrap: `-noconfig` передаётся в командной строке, а не в .rsp (иначе CS2023);
  ссылки — управляемые dll фреймворка, отобранные `AssemblyName.GetAssemblyName` (нативные отсеиваются сами). `server-build.ps1`
  пишет `Tools/out/server/host.txt` — какой `dotnet.exe` запускает сборку; `server-test.ps1` читает его. Без SDK `-Mode Auto` = Bootstrap.
- D-091 (S3.2) — **Пакет данных: формат, хэш, состояние матча.** (1) `ArenaContent.bytes` = заголовок 18 Б (u32 магия «ARNC»,
  u16 `ContentPackHeader.CurrentFormatVersion`, u32 длина тела, u64 `ContentHash`) + тело: поля Defs в порядке объявления, int —
  zigzag varint, float — побитово, bool — бит, enum — varint, строки — UTF-8 с длиной + 1 (0 — null), необязательные объекты — бит
  присутствия, массивы — длина + 1. У пакета своя версия формата, отдельно от `NetProtocol.Version` (уточняет D-068): пакет может
  поменяться без смены протокола и наоборот; несовпадение данных и так ловит хэш. Хэш — первые 8 байт SHA-256 тела big-endian
  (hex равен началу hex SHA-256). (2) Ридер не валидирует Defs (это `ContentBundle.Validate`), длины массивов не больше оставшихся
  бит — битый файл не выделит гигантский массив; ошибки — `InvalidDataException`. (3) Карты: `GameDatabase.AcornsMaps` (списки по
  режимам); в пакете `DefaultMap` первая, затем карты режимов без повторов, `ContentModeMaps` хранит индексы. Политика матча — уровень
  и `UnlockAllAbilities` из `MatchRunnerConfig`. (4) `StateHash` (FNV-1a 64) обходит поля `MatchState` рефлексией в порядке
  `MetadataToken` — новое поле состояния попадает в хэш без правок; выделяет память, только для диагностики. (5) `HeadlessMatch`
  и `MatchSetupBuilder` (раскладка слотов как `MatchSetupFactory`) — в `Arena.Net`: их используют self-test сервера и тесты.
  (6) Сервер грузит пакет рядом с dll при старте (без него — код 3), `--version` печатает хэш. (7) `*.bytes binary` в
  `.gitattributes` — иначе `autocrlf` испортил бы пакет. Причина: Server-Spec §4.1, §5.4; один файл — одни биты на клиенте и сервере.
- D-092 (S3.3) — **«Последний зверь» в симуляции.** (1) Общий спавн — символ `S`, `MapSpawn.Team = MapSpawn.SharedTeam` (−1),
  `MapConfig.RequiredSharedSpawns` (10 у королевской карты, 0 у командных; центральная симметрия не требуется); слоты получают
  спавны перестановкой Фишера–Йейтса на `DeterministicRng` по сиду (`MatchSetupBuilder.CreateFreeForAll`), команда = слот.
  (2) Туман: первый шаг в 0:40, затем каждые 20 с; безопасный прямоугольник вокруг центра карты сжимается на 2 клетки с каждой
  стороны (по каждой оси до полуразмера 2,5); урон в секунду = 500 + 250 × (шаг − 1), импульс каждые 0,5 с, первый — через 0,5 с
  после шага. Урон тумана идёт через `DamageSystem` с источником −1 (ульту не заряжает, убийство никому не засчитывается);
  снижение урона (каска Бруно) на него действует — единая точка здоровья. (3) Места: выбывший в тике получает `ModeState.AliveCount`
  (живые после прошлого обновления режима) — выбывшие в одном тике делят место; если не осталось никого, 1-е место — у того из
  них, кто нанёс больше урона, затем у меньшего слота; по страховочному пределу живые ранжируются по HP, урону, слоту.
  `WinnerTeam` = команда победителя (= слот). (4) Ящики (`BoxState`, `SimLimits.MaxBoxes` = 64) есть только в «Последнем звере»
  (в других режимах тайл `$` остаётся неразрушимой стеной). Урон по ящику — значение вражеских эффектов `Damage` способности
  с уровнем, ягодами, процентом выстрела и долей импульса; ульту не заряжает и в `DamageDealt` не идёт. Бьют: снаряд, остановленный
  клеткой ящика; конус (клетка задета кругом дальности, её центр в конусе, до ближайшей точки клетки нет стены); круг — зона вокруг
  себя, взрыв, мина, импульс поля. Рывок ящики не бьёт (в ТЗ его нет). Сломанный ящик → `Floor`, `TileBroken`, первая ягода — в
  центре клетки. (5) Ягоды: множитель урона после таланта, `MaxHealth` пересчитывается при подборе (текущее HP растёт на прибавку).
  Общий код подборов вынесен в `PickupSystem` (порядок вызовов RNG у желудей тот же — старые тесты и хэш «Жёлудей» не изменились).

  и два поля `BotBehaviourDef`; `NoRespawn` не хранится — его ставят `ContentBundle.CreateMatchDefs` и
  `ConfigConverter.ToLastBeastMatchDefs`. (8) Боты: `BotAction.FleeFog` (вес из данных, выше всего), цель режима — ближайшая
  ягода вне тумана, иначе центр; отступление без своих спавнов идёт к центру карты. Наблюдение: 10 ботов сходятся в центре и
  матч обычно кончается за 30–45 с, до тумана или на 1-м шаге — поведение и темп настраиваются в S3.14 (виды, камера, боты).

- D-093 (S3.4) — **Транспорт: реализация и уточнения ТЗ §3.2.** (1) `Arena.Net.Transport`: `NetConnection` (acks Фидлера +
  окно повторов, RTT по RFC 6298 без экспоненциального отката RTO, надёжный канал, лимиты, проверка пути), `ServerTransport`,
  `ClientTransport`, `ConnectionTable` + `ConnectionIdMap` (открытая адресация), `Handshake` (cookie = SipHash-2-4 от адреса,
  порта, nonce и отрезка времени `CookieSliceMs`; действует в своём и следующем отрезке), `RateLimiter` (таблица 1024 корзин
  по хосту, вытеснение самой старой), `InMemoryNetwork` (часы в мкс, Гилберт–Эллиотт, дубли, перестановка, полоса, тестовый
  `SendFilter`). Всё однопоточно, без аллокаций в установившемся режиме (тесты `AllocationAssert`; слот соединения выделяет
  буферы при первом использовании). Серверные классы транспорта лежат в `Arena.Net` (их немного, ТЗ так и перечисляет), в
  `Arena.Net.Server` (Editor-only asmdef, создан в S3.4) — только `PortableUdpServerSocket`. (2) Надёжный канал: приёмник
  **зеркалит кольцо отправителя** — каждое сообщение несёт своё смещение в кольце 8 КБ, раннее сообщение кладётся по тому же
  смещению; отправитель освобождает место строго по порядку и только после подтверждения, поэтому место, которое он переиспользует,
  у приёмника уже доставлено — буферизация не может переполниться, память = одно кольцо. Сообщение помнит два последних пакета,
  в которых ушло. Формат секции: `varuint count; (u16 id, u16 offset, varuint len, bytes)`. `SendReliable` при полном окне/кольце
  возвращает false и **не закрывает** соединение — решает приложение (`DisconnectReason.ReliableOverflow` есть). (3) Заголовок:
  флаг `HasAcks` (бит 2) — поля ack валидны (иначе ack = 0 у ещё ничего не получившего выглядел бы подтверждением пакета 0);
  `Signed` (бит 3) зарезервирован. `PathChallenge`/`PathResponse` — голый 18-байтный заголовок, 64 бита вызова — в полях
  sequence/ack/ackBits: вызов никогда не больше пакета, который его вызвал, и смену адреса запускает даже пакет keepalive.
  Вызов отправляется только после принятого (нового) пакета — повтор чужого пакета с другого адреса ничего не запускает.
  `Disconnect` = заголовок + байт причины. `Ping`/`Pong` — по 32 Б, `Discover`/`DiscoverReply` — по 48 Б. (4) `ConnectAccepted`
  несёт транспортные параметры (keepalive, таймаут, лимиты сервера); частота снапшотов и избыточность ввода — в `MatchStart` (S3.6).
  Повторный `ConnectResponse` с другим nonce с того же адреса и порта (клиент перезапустился) закрывает старое соединение.
  (5) Числа §13 для транспорта и тестовые недостающие (`InitialRtoMs` 500, `MaxRtoMs` 2000, `HandshakeRetryMs` 250,
  `CookieSliceMs` 10 000, `AckDelayMs` 20, `PathChallengeRetryMs` 250, `RateLimitDisconnectMs` 5000) — PROTO в одном месте:
  `TransportSettings.CreateDefault()`; S3.9 читает их из `server.json`, S3.10 — из `NetConfig`. (6) Сокеты: клиентский
  `UdpDatagramSocket` под Mono в EditMode **не выделяет** память в `Send`/`TryReceive` (тест на loopback) — на телефоне (IL2CPP)
  проверить в S3.10b. SIO_UDP_CONNRESET выключается и у клиентского сокета. В `PortableUdpServerSocket` и `UdpServerSocket`
  перед `ReceiveFrom` — `Available`/`Poll(0)`, чтобы «пусто» не шло через исключение (перегрузок с `out SocketError` у
  `ReceiveFrom` нет). `UdpServerSocket` (.NET 8+, `SocketAddress`) написан, но **не скомпилирован** — SDK нет (Q-012); self-test
  на bootstrap идёт через портативный сокет (≈ 160 Б на пакет). Причина: Server-Spec §3.2, §3.3, §4.6, S3.4.
