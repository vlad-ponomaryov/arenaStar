# Архитектурные решения

Формат: `D-NNN — решение. Причина.` Новые решения дописывать в конец (следующий свободный номер), с шагом и датой.
Числа, которых нет в GDD и которые выбрал агент, — с пометкой `PROTO` (раздел в конце).

## Базовые (план, 2026-10-18)

**D-001 — Своя симуляция боя вместо Photon Fusion 2 на этапе 2.** `Arena.Core` — детерминированная симуляция по тикам 30 Гц
с отдельной структурой ввода. GDD §12.2 требует Fusion в режиме Single, но SDK требует регистрации, а аккаунты создавать нельзя.
Причина: бой останется «под сеть» — на этапе 3 Fusion подключается обёрткой (D-038) без переписывания логики.

**D-002 — `Arena.Core` — чистый C# (`noEngineReferences: true`), состояние — blittable struct в предвыделенных массивах.**
`MatchState` содержит `MatchGlobals` и массивы `FighterState[]`, `ProjectileState[]`, `AreaState[]`, `StatusEffectState[]`,
`PickupState[]`, тайлы карты, `ModeState`. Никаких ссылочных полей, строк и списков в состоянии. Снапшот — `CopyFrom` (Array.Copy).
Причина: логика тестируется без движка, запускается на headless-сервере, состояние легко снимать/восстанавливать и маппить
на `NetworkArray<T>` Fusion; нет аллокаций в тике.

**D-003 — Время в состоянии — тики (`int`), здоровье и урон — `int`.** Конфиги хранят секунды/проценты; конвертер переводит
в тики (`SimTime.SecondsToTicks`, округление к ближайшему). Причина: точные сравнения, совместимость с `TickTimer` Fusion,
нет накопления ошибок float в таймерах.

**D-004 — Ёмкости массивов — константы `SimLimits`** (`MaxFighters = 10` под королевскую битву, `MaxProjectiles = 256`,
`MaxAreas = 64`, `MaxStatusEffects = 128`, `MaxPickups = 64`, `MaxEvents = 256`, `TickRate = 30`). Это технические пределы,
а не игровые параметры — исключение из правила «нет магических чисел». Причина: `[Capacity(N)]` у Fusion должна быть константой
компиляции; переполнение обрабатывается без исключений (счётчик отброшенного).

**D-005 — Математика: свой `Vec2` на `float` и `System.MathF`; RNG — свой struct (xorshift128+/PCG32), seed и состояние — в
`MatchGlobals`.** Требуется детерминизм в пределах одной сборки/платформы (проверяется тестами), побитовый детерминизм между
платформами не нужен: сервер на этапе 3 авторитарный. Причина: проще и быстрее fixed-point, достаточно для авторитарной модели.

**D-006 — Ввод: `struct PlayerInput { Vec2 Move; Vec2 Aim; InputButtons Buttons; }`** — аналог `INetworkInput`.
`Move` и `Aim` — длина ≤ 1; `Aim` — направление × доля дальности (для навесных атак). `InputButtons` (`[Flags] byte`):
`Attack`, `Ult`, `Trick`, `AutoAim`. Кнопки «выстрел» одноразовые: локальный сборщик защёлкивает нажатие до ближайшего тика
и выдаёт его ровно в одном `PlayerInput`; симуляция дополнительно хранит `PrevButtons` в `FighterState` и реагирует на фронт.
Причина: стик «потяни-отпусти» даёт событие между тиками — его нельзя потерять; фронт защищает от повторов при ресимуляции.

**D-007 — Автоприцел считается в симуляции**, а не на клиенте: флаг `AutoAim` → `TargetingSystem` выбирает ближайшего видимого
команде стрелка врага в радиусе атаки, иначе — по направлению взгляда. Причина: серверная проверка (GDD §8.1), одинаковое
поведение у игрока и бота.

**D-008 — События тика (`SimEventBuffer`: попадание, смерть, возрождение, выстрел, подбор, поломка стены, ульта готова) —
вне снапшота**, очищаются в начале каждого тика; виды читают их после тика. Причина: обратная связь (числа урона, вспышки)
без опроса всего состояния; на этапе 3 события восстанавливаются клиентом из состояния/RPC.

**D-009 — Координаты.** Core `Vec2(x, y)` ↔ Unity `(x, 0, y)`; 1 клетка = 1 юнит; клетка `(c, r)` имеет центр `(c+0.5, r+0.5)`;
начало карты — `(0, 0)`, команда 0 внизу (малые `y`), команда 1 вверху. Причина: однозначное соответствие сетки и мира.

**D-010 — Данные: ScriptableObject-конфиги → чистые Core-Defs.** Классы SO — `Assets/_Project/Scripts/Data` (asmdef `Arena.Data`,
ссылается на Core и Bots), ассеты — `Assets/_Project/Data/{Fighters,Maps,Modes,Combat,Bots,Feel,Localization,Economy}`.
Корневой SO `GameDatabase` ссылается на всё; сцены ссылаются на него (без Resources/Addressables на этапе 2). Ассеты создаёт
`Arena.Editor.Data.DataSeeder.SeedAll`; **на этапе 2 сидер — источник правды и перезаписывает значения** (идемпотентно).
Причина: агенты не открывают редактор; после начала ручного тюнинга сидер переключим на «создавать только отсутствующие» (Q-005).

**D-011 — Способности = доставка + эффекты + условные модификаторы.** `AbilityDef { DeliveryKind; параметры доставки;
EffectDef[] }`, `EffectDef { EffectKind; TargetFilter (Enemy/Ally/Self); Value; Duration; Distance }`,
`TalentDef { TalentCondition; TalentModifier; Value; Param }`. Атака, ульта и трюк используют один `AbilitySystem`.
Эффекты — маленькие статические обработчики (`DamageEffect`, `KnockbackEffect`, `StunEffect`, `HealEffect`, `DashEffect`,
`ShieldEffect`/`DamageReduction`, `InvisibilityEffect`, `MarkEffect`, …). Новый боец — новые данные. Причина: GDD §4, §12.2.

**D-012 — Уровни в прототипе.** `MatchSetup` хранит уровень бойца (по умолчанию 1) и флаг `UnlockAllAbilities = true`:
трюк и талант доступны сразу, хотя по GDD открываются на 5 и 8 уровнях. Причина: тестерам нужно попробовать весь бой;
прокачки нет до этапа 4. Вопрос — Q-003.

**D-013 — Числа, которых нет в GDD** (скорости снарядов, радиусы бойцов, интервалы очередей, порог заряда ульты, сила «лёгкого
отброса», радиус обзора бота, задержки), агент выбирает сам, кладёт **только в сидер** и записывает в раздел PROTO ниже.

**D-014 — Виды: префабы и материалы создаются кодом (`ViewAssetBuilder`), рантайм — пулы.** Префабы в `Assets/_Project/Art/Prefabs`,
материалы (URP Lit/Unlit) — в `Assets/_Project/Art/Materials`, ссылки — через SO `ViewCatalog`. В рантайме нет `Shader.Find` и
`GameObject.CreatePrimitive`. Смена цвета (вспышка, полупрозрачность в кусте, свой/чужой) — подменой общего материала,
не `MaterialPropertyBlock`. Причина: шейдеры не вырежутся из сборки, SRP Batcher работает, арт заменяется правкой префаба.

**D-015 — Отображение интерполирует между двумя последними тиками; предсказания офлайн нет; стоп-кадр ульты — только визуальный.**
Причина: офлайн задержка ≤ 1 тика (33 мс); на этапе 3 добавится предсказание своего бойца (GDD §8.1). Стоп-кадр в симуляции
невозможен на сервере, поэтому замораживаются только виды на 40 мс.

**D-016 — Камера:** фиксированный угол ~55° (из `CameraConfig`), по горизонтали — центр карты, по длинной оси следует за игроком
с ограничением краями карты. Для команды 1 камера повёрнута на 180° вокруг центра карты, и ввод поворачивается так же
(в `LocalInputCollector`), — «своя база внизу». Причина: GDD §5.5; карта 21×31 целиком на экран телефона не влезает.

**D-017 — Ввод: только Input System (`activeInputHandler = 1`).** Сенсорные стики — uGUI (`IPointer*Handler` через
`InputSystemUIInputModule`), ПК/редактор — прямой опрос `Keyboard.current`/`Mouse.current` (без `InputActionAsset`).
Всё сводится в `LocalInputCollector` → `PlayerInput`. Причина: один путь для мыши и касаний, без аллокаций, без GUI-настройки.

**D-018 — UI строится в рантайме кодом** по SO `UiStyle` (размеры, отступы, цвета, встроенные спрайты `UI/Skin/*`).
Шрифт этапа 2 — встроенный `LegacyRuntime.ttf` (uGUI `Text`, динамический, кириллица через системный фолбэк).
TextMeshPro + Rubik/Nunito (OFL) — на этапе 5. Причина: импорт TMP Essentials в batchmode — лишний риск ночью; без внешних шрифтов.

**D-019 — Локализация этапа 2 — своя таблица** `LocTable` (SO: ключ, en, ru) + `Loc.Get(key)`; ключи — константы `Loc.Keys`.
Переход на Unity Localization — этап 4–5. Причина: Unity Localization тянет Addressables и отдельный шаг сборки контента;
в прототипе мало строк. Вопрос — Q-004.

**D-020 — Активная платформа проекта всегда Android** (`-buildTarget Android` во всех запусках). Сборка: IL2CPP, ARM64,
minSdk 26 (Android 8.0), Vulkan + GLES3, ASTC, только landscape, APK (не AAB) в `Builds/Android/`.
Причина: нет переимпорта при переключении платформ; параметры — GDD §8.4.

**D-021 — Проект создаётся `-createProject` без шаблона URP**, URP и прочее — пакетами и кодом. Причина: шаблон приносит
примеры, лишние пакеты и ассеты; чистый проект детерминированно настраивается `ProjectConfigurator`.

**D-022 — Боты — отдельный чистый asmdef `Arena.Bots`** (ссылается на Core), с собственным RNG в состоянии бота, решения
раз в 0,2 с. Бот видит только врагов, видимых его команде (кусты, невидимость), и в радиусе обзора (`PROTO`, ≈ размер экрана) —
аналог «не знает позиций за пределами экрана». Причина: GDD §7; боты пойдут на сервер этапа 3 без изменений.

**D-023 — Пакеты ставятся `UnityEditor.PackageManager.Client.AddAndRemove`** из Editor-скрипта без указания версий
(Package Manager выбирает рекомендованные для редактора); запасной путь — версии в `manifest.json`. Состав: URP, Input System,
Test Framework, uGUI; убираются collab-proxy, visualscripting, multiplayer.center, timeline. Причина: агент не угадывает версии.

**D-024 — Видимость.** Боец виден чужой команде, если выполняется хотя бы одно: не в кусте и не невидим; враг этой команды
ближе `BushRevealDistance` (2 клетки; к невидимому — не действует); боец атаковал за последние 1 с (раскрытие, снимает и
невидимость); помечен этой командой (метка Новы); у команды активно раскрытие (ульта Новы). Союзники видят друг друга всегда.
Своего бойца в кусте рисуем полупрозрачным. Невидимость (трюк Векса) скрывает на любом расстоянии, пока не атакует.
Причина: GDD §5.2 + однозначные правила для тестов и ботов.

**D-025 — «Жёлуди», уточнения.** Золотой жёлудь — дополнительно к обычному на 60 и 120 с. При поражении бойца его жёлуди
рассыпаются как обычные (золотой = 3 обычных), подобрать можно через `PickupDelay` (`PROTO` 0,5 с). Отсчёт идёт для команды
с бо́льшим числом желудей, если у неё 12+; при равенстве 12+ отсчёт сбрасывается. Подбор — касанием (радиус бойца + радиус
жёлудя). Причина: GDD §5.4 не описывает эти случаи.

**D-026 — Бойцы не сталкиваются друг с другом**, только со стенами и водой. Причина: стандарт жанра, меньше застреваний и
рассинхрона на этапе 3.

**D-027 — Без динамических теней:** под бойцами — тени-кружки (квад с прозрачной текстурой, сгенерированной кодом). Причина: GDD §8.4.

**D-028 — Звуки этапа 2 — процедурные** (`AudioClip.Create` из синусов/шума при старте, параметры в `FeelConfig`). Причина:
нет ассетов и лицензий; оригинальный контент.

**D-029 — Палитра команд:** свои — синий, враги — красный, с заметной разницей яркости; в настройках — палитра для дальтоников
(синий/оранжевый). Цвета — в `UiStyle`/материалах. Причина: GDD §5.3.

**D-030 — Мина Чомпа** видна своей команде всегда, врагам — по правилам видимости кустов (ближе 2 клеток). Причина: в GDD не задано;
иначе мина бесполезна.

**D-031 — Возрастной гейт — на этапе 4** (вместе с аккаунтом). Прототип этапа 2 не собирает данных, не имеет чата, рекламы, ссылок и
покупок — соответствует «ограниченному режиму». Вопрос — Q-001.

**D-032 — Сцены `Boot`, `Menu`, `Match` целиком генерирует `SceneBuilder.BuildAll`** и содержат только бутстрап-объекты (камера, свет,
EventSystem, раннер со ссылками на SO). Карта, бойцы, HUD создаются в рантайме из данных. Причина: YAML не пишем руками, сцены
пересоздаются без конфликтов.

**D-033 — Инструменты и проверки.** `Tools/*.ps1` совместимы с PowerShell 5.1, всё пишут в `Tools/out/`, итог — одной строкой, коды
0/1/2/3. Отсутствие аллокаций проверяется тестом через `GC.GetAllocatedBytesForCurrentThread()` после прогрева; детерминизм — двумя
симуляциями и снапшотом. Причина: агенты работают только через batchmode, итог должен читаться машинно.

**D-034 — Идентификатор пакета `com.arena.prototype`, отладочный keystore.** Причина: юрлицо и название не выбраны (GDD §13);
для теста на телефоне подписи отладки достаточно. Вопрос — Q-002.

**D-035 — На этапе 2 нет папки `Net` и режима «Тренировка».** Тренировка = матч с ботами «Новичок» (выбор в меню). Причина: этап 2
по GDD §3 — только «Жёлуди»; пустые папки дают в git «висящие» `.meta`.

**D-036 — Движение мгновенное, без инерции:** скорость сразу равна `move × speed`. Причина: отзывчивость, проще предсказание на этапе 3.

**D-037 — Частота кадров:** `Application.targetFrameRate = 60`, `vSyncCount = 0`, настройка «экономия» — 30. Причина: GDD §8.4.

**D-038 — План подключения Fusion (этап 3).** Один `NetworkObject` «Match» с `NetworkBehaviour`, который в `FixedUpdateNetwork`
собирает `PlayerInput` всех игроков (`GetInput`), вызывает тот же `MatchSimulation.Tick`, а массивы состояния лежат в
`[Networked, Capacity(SimLimits.X)] NetworkArray<FighterState>` и т. п. (struct станут `INetworkStruct`). `MatchRunner` этапа 2 — это
локальная реализация того же цикла. Причина: фиксирует ограничения для Core уже сейчас (blittable, константные ёмкости, тики).

**D-039 — Журнал ночи:** после рабочего коммита шага строка в `Docs/NightLog.md` с его хешем — отдельным коммитом `docs: night log Sx.y`.
Причина: хеш известен только после коммита; история не переписывается.
