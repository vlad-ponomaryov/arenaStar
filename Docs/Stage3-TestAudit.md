# Этап 3 — аудит тестов (статический, 18.10, ничего не менялось)

Сделан помощником остановленного верификатора. Пороги в тестах совпадают с §11.1 ТЗ; ничего не отключено (Ignore/Explicit/Assert.Pass); проверка аллокаций имеет положительный контроль; компенсация лага проверена настоящим тестом на 2 клиентах. Слабое место — заявление «без рассинхрона и телепортов». Список для завтрашней верификации:

- **W1. Предсказание точно «по построению».** В тестах сервер и клиенты — один процесс, один Mono, один `ContentBundle`, поэтому ошибка предсказания ровно 0. Реальная пара CoreCLR-сервер ↔ Mono/IL2CPP-клиент (по D-064 расходятся с тика 83) не тестируется. Исправить: тест против настоящего процесса Arena.Server с клиентами-ботами Unity (как в LoadTest), или искусственно сдвинуть MoveSpeed тени на 1e-4 и проверить p99 < 0.05 и 0 телепортов.
- **W2. CI-условия вдвое слабее GDD на поток.** `MatchServerRig.cs:32`: 1 % потерь и джиттер 0–25 мс на каждое направление, а GDD — 2 % и 50 мс. Добавить прогон {75 мс, 50 мс, 2 %} на направление или записать трактовку в Decisions.md.
- **W3. Детектор телепортов слеп к прыжкам > 3 клеток** (`PresentationState.cs:247,277-283`) и ни один тест не показывает, что он срабатывает. Считать прыжок между двумя видимыми кадрами телепортом; юнит-тест: прыжки 1.5 и 4 клетки → Teleports == 2.
- **W4. «Внешние» коррекции исключают слишком много** (`Predictor.cs:251-255`: урон, заряд ульты, рывки, трюки). Проверять ExternalSamples < 50 %, исключать только то, что меняет позицию.
- **W5. Проверка результата — по сути проверка кодека** (`OnlineMatchTests.cs:86-102`); позиции чужих бойцов с сервером не сравниваются. Сравнивать видимые позиции с историей сервера на RenderTick.
- **W6. Плохая сеть недопроверена** (`OnlineMatchTests.cs:171-184`, `LongOnlineTests.cs:21-33`): нет проверки аллокаций, минимума сэмплов, «нет перехвата ботом», трафика.
- **W7. Проверка max ≤ 1200 Б не может упасть** — кодер и так режет до 1100. Проверять DeferredItems == 0.
- **W8. Проверки видимости/AOI могут пройти вхолостую** — счётчики только печатаются. Проверять > 0; AOI снарядов — по позиции сегмента на тике вида.
- **W9. Временные пороги нестабильны:** вечером self-test один раз упал (lateness p99 18 мс ≥ 2), нагрузка 100 матчей — FAILED (p99 5.52 > 5 мс), вероятно из-за параллельного Unity. Self-test не делает проверок §11.1 (`HostSelfTest.cs:175-191`). Гейт по lateness — только на простаивающей машине или с повтором.
- **W10.** Долгий тест создаёт новый стенд на каждый матч — утечки между матчами не ловит. Один MatchHost, 10 матчей подряд.
- **W11.** «Чужие интерполируются» в PlayMode истинно по построению (`OnlineMatchSceneTests.cs:101/112`).
- **W12.** Аллокации меряются 2 с в середине матча (без ульт/смертей/конца); bootstrap-сокет сервера аллоцирует ~160 Б/пакет (допустимо по §4.6); порядок смены адреса не проверяется (`ConnectionTests.cs:140-152`).
- **W13.** Обнаружение «UDP заблокирован» и «Обновите игру» (`OnlineSession.FailureOf`) не тестируется.
- **W14. Мелочи:** нет негативного теста ReplayVerifier; нет дрейфа часов клиент/сервер в стенде; трафик без 28 Б заголовков IP/UDP (всё равно ~3.9/1.8 КБ/с); лобби на 7–11 клиентов не тестируется; нет проверки, что боты реально дрались.

# Ревью клиентской (Unity) части этапа 3 (статическое, 18.10)

Критических дефектов нет. Находки:
1. **Важно: без сервера из онлайн-матча не выйти.** `UI/Hud/ConnectionOverlay.cs:95-107,133-137`: после GaveUp есть только «Вернуться в матч» (ещё 60 с попыток, по кругу); в HUD нет кнопки меню и обработки Android Back. При закрытии соединения сервером (`Closed`/`ServerShutdown`) `ReconnectState` остаётся `None`, отсчёт идёт до 0, кнопки нет вообще. Исправить: кнопка «Меню» (`LocKeys.ResultsMenu` → `SceneFlow.ToMenu`) в GaveUp; Lost + None + disconnected считать GaveUp. PlayMode-тест: убить сервер посреди матча → GaveUp → Меню.
2. LAN-сервер в обслуживании/остановке показывается как «Обновите игру» (`Online/OnlineSession.cs:465-475`) — должно быть `OnlineFailure.Maintenance`.
3. DNS-регион: поиск и пинг берут разные адреса (IPv6 первым vs IPv4) — `OnlineSession.cs:281,486` vs `RegionPingService.cs:180,208-214`; DNS-вызов в `Search` без try/catch может застрять в `Locating`.
4. «Ещё раз» после «Вернуться в матч» из меню (новый запуск) не встаёт в очередь: `UpdateRejoin` не ставит `_hasLastSearch`; экран поиска показывает «Жёлуди» для «Последнего зверя».
5. `RejoinStore.Clear()` не удаляет ключи `arena.rejoin.*` из PlayerPrefs (§6.4 требует удаления).
6. Параметры транспорта клиента — константы в коде (`TransportSettings.CreateDefault()`), а не `NetConfig` (правило «нет магических чисел», §13).
7. `OnlineSession` — 670-строчный MonoBehaviour без EditMode-тестов; вынести логику в `OnlineSessionCore`; `_pings` не останавливается в `Close`/`OnDestroy`.

Проверено и верно: синглтон и сцены, пауза/возврат, потоки, rejoin, отсутствие аллокаций в кадре, Loc-ключи EN/RU, asmdef (Core/Bots/Net без движка, Net.Server только Editor), dev-инструменты только в debug, офлайн-тренировка, камера/ввод, HUD, итоги, настройки сборки.

# Ревью сервера матча и лобби (статическое + пробы, 18.10)

Критических и крупных дефектов нет; фаззинг (~290 тыс. случайных сообщений, 36 тыс. кадров враждебного ввода) — без исключений, все 38 комнат прошли `ReplayVerifier`. Мелкие (8 из 9 подтверждены пробами; исходники проб были в scratchpad сессии):
1. Поздно доставленное нажатие может «съесть» следующее (`Net/Server/Match/SlotInputBuffer.cs:252`) — нарушает D-006 «нажатия не теряются». Откладывать pending-нажатие, если у буферизованного ввода на tick+1 та же кнопка.
2. Подключённый игрок без `ClientReady` получает бота только с 45-го тика, а не на старте (`MatchRoom.cs:243,276-283`) — дать причину `NotReady` в `EnterCountdown`.
3. «Последний зверь»: выбывший игрок, нажавший «Ещё раз» (Leave), получает бота за мёртвого бойца (`MatchRoom.cs:167,177` — нет проверки `NoRespawn && !Alive`, как на :314).
4. Повтор при пропущенном вводе теряет `ViewDelayTicks` (`SlotInputBuffer.cs:212`) — рывок/очереди на таком тике без перемотки.
5. Комната, из которой ушли все люди, продолжает идти (держит слот `MaxMatches`, CPU, растягивает остановку) — завершать/закрывать.
6. `ClientStats` портят метрики: переупорядоченный пакет считается дважды, огромные значения раздувают счётчики (`MatchRoom.cs:195-203`) — учитывать sequence, ограничивать рост и max.
7. `arena_takeovers_total` недосчитывает перехваты от Leave/отключения (`MatchRoom.cs:316-318`).
8. `QueueRejected(InMatch)` никогда не отправляется: `ServerNode.cs:138` отдаёт всё от соединения матча в `MatchHost` (`Matchmaker.cs:152` — мёртвый код).
9. Метрика `NoFreeRoom` считает проходы цикла, а не события (`Matchmaker.cs:188`).

Проверено и верно: жизненный цикл комнаты, буфер ввода, ограничение перемотки, санитизация и порядок для повтора, перехват ботом, rejoin, лобби и обслуживание, отсутствие Dictionary/DateTime/аллокаций в логике.

# Ревью Arena.Core и Arena.Bots за этап 3 (статическое + пробы, 18.10)

Критических дефектов нет. Предсказание (17 тыс. теневых тиков без нарушений), компенсация лага (180 тыс. проверок истории позиций без расхождений), CopyFrom/StateHash, правила «Последнего зверя» (154 матча по 10 ботов — всегда ровно один победитель) — проверены пробами.
1. **Важно (боты, редко): HideInBush выбирает куст в тумане** → бот мечется «спрятаться/бежать от тумана» каждые 6 тиков, пока туман его не убьёт. `Bots/BotController.cs:466-487` (`FindHideBush`), вызов 270-274. Исправление (проверено на копии: 24 → 3 переключения на 100 матчей): пропускать кусты, где `LastBeastRules.IsInFogSoon(state, defs, center, _behaviour.FogWarnTicks)`; то же для CheckBush (`FindBushMemory`/`FindNearestBush`). Не учитывают туман и цели Attack/CheckBush/BreakBox. Тест: карта 21×21, бот с 20 % HP у кромки → `brain.Goal` никогда не в тумане.
2. Только первый шаг тумана даёт 0.5 с до урона; на следующих шагах урон в тот же тик (`Core/Modes/LastBeastRules.cs:41,61-63`). Если нужна пауза — `m.NextFogPulseTick = now + lb.FogPulseTicks` при шаге; иначе задокументировать. **Вопрос к человеку.**
3. Урон тумана в секунду «плывёт» при другой длине импульса из-за усечения (`LastBeastRules.cs:110`) — делить как `EffectContext.Portion` или валидировать кратность.
4. `LootRadiusCells` — квадрат для ящиков (`BotController.cs:585`) и круг для ягод (`:249`) — выбрать одну метрику.

Наблюдение: темп ботов сильно зависит от сида (35–186 с за 24 матча; иногда матч кончается до первого шага тумана) — утверждение S3.14 «матч дольше старта тумана» держится только на сидах 1 и 42.
